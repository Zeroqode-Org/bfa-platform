---

`/wp/notices` is where a water purveyor decides what its customers read. Three
things share the screen and share almost nothing else:

- **Notice templates** — the stored subject and message for each of the four
  automated notices. The scheduler sends them, about one assembly — see
  [Notice Workflow & Scheduler](/docs/notice-workflow).
- **General info broadcast** — a one-off message composed and sent now, to a
  filtered set of customers. It does not touch `notice_templates`.
- **Repair companies** — read-only, because a failure notice names them.

This page describes the screen as built. It covers *WP dashboard — notices and
email settings* in the [build plan](/docs/build-plan) and PRD § 6.6.7.

## The four notice templates

One row per purveyor per type in `notice_templates`, keyed on
(`water_purveyor_id`, `notice_type`):

| Type | When it is sent |
|---|---|
| `reminder` | Two calendar months before the assembly's `annual_test_date` |
| `late_notice_1` | The due date **+ 1 day** |
| `late_notice_2` | The due date **+ 32 days** — 31 after late notice 1 |
| `final_notice` | The due date **+ 63 days** — 31 after late notice 2 |

Those dates are computed from `bfa_assets.annual_test_date` and evaluated in
Pacific/Honolulu; the intervals are platform constants and not purveyor
configuration (PRD § 9). The reminder additionally carries the list of testers
the customer can call, appended below the purveyor's own text. See
[Notice Workflow & Scheduler](/docs/notice-workflow).

### A missing row is a meaning, not an absence

`listNoticeTemplates` always returns exactly four entries, one per value of the
`notice_type` enum, whatever the table holds. Where there is no row it returns
the **platform default** text.

That is what a missing row means: this purveyor has not customized this notice,
so the platform's words are what would be sent. Nothing backfills empty rows
when a WP is created, and the screen has no "not set" branch — it opens on text
that is sendable either way, and `isCustomized` is the only difference between
the two cases. A row whose `subject` or `body` is null or blank is treated the
same way, because half a template saved is not a reason to send half an email.

<Callout type="warn">
The platform defaults in `packages/api/src/lib/notice-defaults.ts` are
**provisional product copy and are not approved for production.** The PRD, the
build plan and the prototype all specify the fallback *mechanism* and none of
them specifies the words. What ships is deliberately plain — it states the facts
the purveyor's own records supply, and makes no compliance claim, quotes no
regulation, names no penalty and threatens no interruption of service, because
inventing any of those would put words in a purveyor's mouth that they are
answerable for. The client must supply or approve customer-facing text for all
four types — and the one-line heading above the reminder's tester list — before a
production tenant uses them. **Workflow 1 now sends this copy**, so the approval
blocks switching `automated_notices` on for a real purveyor, not only this
screen. Replacing it is an edit to that one file; nothing else in the feature
contains notice copy.
</Callout>

### There is no enable/disable toggle, deliberately

`notice_templates.is_enabled` exists in the schema, is never read by this
feature and is never written by it. Automated notices are a paid add-on the
Super-Admin switches on per purveyor through
`wp_feature_flags.automated_notices` — a level above a single notice type.

What disabling a *middle* step of the escalation chain would mean is unanswered,
so a per-type switch would be a control with undefined behaviour. The refusal is
enforced in three places rather than one: the field is absent from
`upsertNoticeTemplateInput`, absent from the mutation's `set`, and absent from
the UPDATE grant in `0010_notice_template_policies`, so nothing reaching the
table through PostgREST can flip it either. Workflow 1's handler is the fourth:
it resolves a template without reading the column, so switching automated
notices on or off is the feature flag and nothing else.

## Dynamic values

Placeholders are double braces, matching the syntax already in `seed.ts`.
Surrounding whitespace is tolerated, so `{{ customer_name }}` resolves too.

| Value | Placeholder | Scope | Notice templates | General info |
|---|---|---|---|---|
| Customer name | `{{customer_name}}` | recipient | yes | yes |
| Water purveyor name | `{{wp_name}}` | recipient | yes | yes |
| BFA type | `{{bfa_type}}` | asset | yes | **no** |
| BIN | `{{bin}}` | asset | yes | **no** |
| Service address | `{{service_address}}` | asset | yes | **no** |
| Due date | `{{due_date}}` | asset | yes | **no** |

### One list defines all of it

`packages/api/src/lib/notice-variables.ts` holds the registry: each variable's
placeholder, the label the panel shows, its preview sample, and the `scope` that
decides where it may be used. Nothing downstream names a variable — the editor,
the reference panel, the preview and the renderer all take a list. Adding a
seventh is an entry there plus a value wherever it is resolved.

The module imports nothing, so the browser runs the same `renderTemplate` the
server sends with. The preview and a real send cannot disagree about what a
placeholder means.

### Substitution rules

- **One pass, not one `replace` per variable.** A substituted value is never
  rescanned, so a customer whose name genuinely contains `{{due_date}}` gets
  their name. The order of the registry cannot affect the result.
- **Nothing is executed.** There are no expressions, no template language and no
  conditionals — just named placeholders.
- **Nothing is rendered as HTML.** `templateToHtml` escapes the whole rendered
  string and turns line breaks into paragraphs. Typed text and substituted
  values are both escaped, so a `<` in a customer's name is a `<`. The email
  shell is added *around* that escaped fragment afterwards and never inside it —
  see [The email shell](#the-email-shell).
- **An unresolvable placeholder stays visible.** Unknown, not allowed here, or
  allowed with no value for this record — all three come back written exactly as
  they were. Blanking would let a typo vanish into a sentence that still reads.
  Nothing ever falls back to another variable's value.
- **…and is refused before it can be saved or sent.** The renderer leaves it
  visible; `templateTextError` is what stops `{{custmer_name}}` reaching a
  customer, in both Zod schemas, server-side.

### Why the general-info broadcast gets only two

A broadcast is addressed to a **customer**, and a customer may own several
assemblies. `{{bin}}` therefore has no single value for a recipient — nor does
`{{bfa_type}}`, `{{service_address}}` or `{{due_date}}`. An automated notice is
about **one assembly**, so all six resolve there.

Using one in a broadcast is a validation error with its own sentence, not a
silent blank. The reference panel does not offer the four, and the preview warns
about one typed by hand.

## The general info broadcast

Subject, message, a recipient filter, and a send. Not a template: nothing is
stored in `notice_templates`, there is no scheduler, no history of what was sent
and no scheduled delivery — all deliberately out of scope.

### Recipient filters

| Filter | Selects |
|---|---|
| `all_customers` | Every active customer in the purveyor |
| `agricultural_only` | Active customers on the agricultural rate category |
| `past_due_only` | Active customers who own at least one asset the scheduler has marked `past_due` |

`recipientsFor` in the router is the only definition of the three audiences.
Both the count shown before sending and the loop that sends read it, so the
number on screen is the number of people who receive the message.

### Two product decisions, stated

**Suspended customers are excluded, from every filter.** PRD § 9 confirms that
suspension is "a hold on the whole asset's notice pipeline" rather than a
per-email skip. The requirements did not extend that to general information, so
the safe direction shipped: a purveyor who suspended an account has said they
are not writing to that customer at the moment, and the cost of the other choice
is mail somebody decided not to send. Reversing it is one predicate in
`recipientsFor`.

**Each customer is written to once.** `past_due_only` asks a question about
assemblies, and a customer with three past-due assemblies is still one person
with one inbox. The query uses `EXISTS` rather than a join, so the
de-duplication is structural — there is no row-per-asset to collapse.
`0010` adds a partial index on
(`water_purveyor_id`, `current_customer_id`) `WHERE asset_status = 'past_due'`
for exactly that lookup.

### A partial failure is a failure

Each message is rendered separately for its recipient and sent through
`sendEmail` — the one mail path in the app, which emits a structured line per
attempt whether it succeeded or threw. Nothing here touches a provider SDK, so
the console driver works with no keys configured.

If any send throws, the mutation **refuses** rather than reporting a broadcast
some customers never received. The error names how many succeeded and how many
failed; the per-attempt log lines say which. Nothing retries automatically — a
resend is the Admin's decision, because the customers who did receive it would
get it twice.

An audience with nobody in it is refused too, rather than reported as a send.

## Roles and permissions

| Role | Read templates | Write a template | Send a broadcast |
|---|---|---|---|
| `wp_admin` | own WP | own WP | own WP |
| `wp_sub_admin` | own WP | no | no |
| `wp_employee` | own WP | no | no |
| `certifier` | no | no | no |
| `super_admin` | not through this router | not through this router | not through this router |

All three WP roles read the screen. Only the Admin writes, because both writes
put words in the purveyor's name in front of every customer they have, which is
not clerk work.

That check lives in `wpNoticeAuthorProcedure`, **local to this router** rather
than a shared `wpAdminProcedure` — the same reasoning as `submitted-tests.ts`.
The SubAdmin/Employee split is open project-wide (PRD § 10) and this does not
close it; a shared procedure would read as a project-wide answer the next
feature could inherit by accident. Widening it later is one predicate; narrowing
it takes access away from people who had it.

A Super-Admin is **refused**, not quietly handed the first tenant's templates.
Cross-tenant access would be a separate, deliberately designed endpoint.

## Procedures

`notices.*` in `packages/api/src/routers/notices.ts`.

| Procedure | Base | Does |
|---|---|---|
| `listNoticeTemplates` | `wpProcedure` | All four types, saved text or platform default, with `isCustomized` |
| `getNoticePreviewSample` | `wpProcedure` | Sample values for the preview, with the purveyor's real name on `{{wp_name}}` |
| `upsertNoticeTemplate` | `wpNoticeAuthorProcedure` | Writes one template — creates on the first save, rewrites after |
| `getBroadcastAudience` | `wpProcedure` | How many customers a filter selects, and a sample recipient |
| `sendGeneralInfoBroadcast` | `wpNoticeAuthorProcedure` | Renders and sends one message per recipient |

### Tenant scoping

The tenant is never an input. No procedure here has a `waterPurveyorId` field,
so a client has nowhere to ask for somebody else's — and Zod strips it if one is
sent anyway. Every query carries `ctx.caller.waterPurveyorId` in its predicate,
including the `EXISTS` subquery on `bfa_assets`, because `current_customer_id`
is a foreign key and nothing in it says the asset shares the customer's tenant.

### A save that changes nothing writes nothing

Both fields are sent on every save, so a request that edits a template and one
that opens it and presses save look identical on the wire.
`upsertNoticeTemplate` reads the stored row first and, when the subject and body
both already hold what is being written, returns it without touching the table.

Writing anyway would make two records lie. `updated_at` would come to mean "when
somebody last pressed save" rather than when the text last changed, and the
audit trail would carry a `notice_template_saved` line for a modification that
never happened — the one thing an audit trail must not do. Same rule as
`updateRepairCompany`.

A **missing** row is never unchanged, even when the text submitted is the
platform default verbatim. Writing it turns "this purveyor uses the platform's
words" into "this purveyor chose these words", and those are different facts:
the platform copy can be revised, and a purveyor who adopted it deliberately
should not be revised with it.

`upsertNoticeTemplate` conflicts on (`water_purveyor_id`, `notice_type`), which
is what makes it an upsert rather than a race two simultaneous saves could lose,
and pins the tenant in the update predicate as well.

These procedures run through the privileged Drizzle connection, which bypasses
RLS. The procedure layer is the application's authorization boundary; the
policies below are a second, independent one.

## Row policies

`0010_notice_template_policies` adds the `notice_templates` policies. RLS was
enabled on the table in the first migration; until now it had no policies at
all, so nothing reaching it through PostgREST could see a row.

| Policy | Who | What |
|---|---|---|
| `notice_templates_all_super_admin` | `super_admin` | Read, insert and update, in every tenant |
| `notice_templates_select_own_wp` | all three WP roles | Read rows in their own purveyor |
| `notice_templates_insert_own_wp` | `wp_admin` | Insert rows into their own purveyor |
| `notice_templates_update_own_wp` | `wp_admin` | Update rows in their own purveyor, and only into it |

Caller resolution goes through the `private.current_global_role()` and
`private.current_wp_id()` helpers from `0001`, so a blocked profile resolves to
NULL and keeps no access at all.

The grants are column lists rather than a bare table grant. Three columns are
deliberately missing from UPDATE:

- **`water_purveyor_id`** — a template never changes tenant. The `WITH CHECK` on
  the update policy says the same thing a second time, for the day a later
  migration widens the grant.
- **`notice_type`** — the pair is the template's identity. Re-typing a row is not
  an edit to it; it is a different template, which the INSERT path creates.
- **`is_enabled`** — see above. Withholding the privilege is what keeps "we did
  not build the toggle" from being only a UI decision.

**No DELETE for anybody, Super-Admin included.** A deleted row is
indistinguishable from one never written, and that absence is what means "this
purveyor uses the platform default" — so there is nothing deleting would express
that rewriting the text does not. As in `0005`, the Super-Admin policy reads
`FOR ALL` and still cannot delete: a policy cannot hand back a privilege the
grant never gave.

## Email delivery path

One path, and the feature has no second one:

```
sendGeneralInfoBroadcast
  → renderTemplate (per recipient; plain text)
  → renderTextEmail (packages/api/src/lib/email-layout.ts)
      → templateToHtml (escapes, line breaks → paragraphs)
      → renderEmailLayout (wraps the fragment in the shared shell)
  → sendEmail (packages/api/src/lib/email.ts)
  → the driver selected by EMAIL_DRIVER (console by default, Resend when provider)
```

Every attempt emits `email_send_attempted` carrying the event, status, recipient,
`actor_id` and `wp_id`. Each message is tagged `type=general_info_broadcast` and
`recipient_filter=<filter>` so delivery logs can be filtered by campaign.
Switching `EMAIL_DRIVER` changes nothing in this feature.

The four notice templates are **stored** here and **sent** by the scheduler,
through the same three calls with one substitution each rather than one per
recipient:

```
scheduler notice handler
  → renderTemplate (the purveyor's row, or the platform default, per column)
  → renderTextEmail
  → sendEmail   (tagged type=<notice_type>, wp_id, asset_id)
```

The handler reads `notice_templates` at send time and applies exactly the
fallback rule described above, so what a purveyor previews here is what a
customer receives. It does not read `is_enabled`. See
[Notice Workflow & Scheduler](/docs/notice-workflow#4-the-text).

### The email shell

A broadcast is delivered inside the same layout as every other message the
platform sends — the one described under
[The shared email layout](/docs/invitations-onboarding#the-shared-email-layout):
a **Backflow Assembly Platform** text wordmark header, the message in a white card, and a
one-line footer. It is table-based with inline styles, loads nothing remote and
carries no tracking.

What the shell does **not** do matters as much:

- **The body stays plain text.** The composer is a textarea, and what a WP Admin
  types is substituted, escaped by `templateToHtml` and only then wrapped. The
  layout inserts that fragment as-is and adds nothing inside it, so `<script>`,
  `<img>`, a link or any other tag typed into a message arrives as visible text,
  never as markup. There is no rich-text editor and no way to supply HTML.
- **The words are not changed.** The subject becomes the document title and is
  not repeated in the body, no greeting or sign-off is added, and paragraphs are
  exactly the lines that were written.
- **No logo.** Branding is text-only until the client supplies a logo asset they
  own; nothing in a message is carried by an image.

`renderTextEmail({ subject, text })` is the function to call, and it is also the
path for **automated notices**: Workflow 1 sends every notice template through
the same call, so a notice and a broadcast share one shell and one escaping rule.
That makes the templates *compatible* with the layout — it does not approve their
words. The platform-default copy is still provisional, as the warning above says.

The on-screen preview shows the substituted text, not the email shell.

## Audit logging

| Event | When |
|---|---|
| `notice_template_saved` | A template is created or rewritten — with `notice_type` and the row id |
| `general_info_broadcast_started` | Before the first send, with the filter and the recipient count |
| `general_info_broadcast_finished` | After the last, with sent/failed counts and `status` of `sent` or `partial_failure` |

Each carries `actor_id`, `wp_id` and `timestamp`, the same shape as
`repair_company_created` and `caller_resolved`.

## The screen

Three stacked sections in the standard WP shell.

**Notice templates.** One tab per type, rendered by looping over the server's
list — not four hardcoded field groups, so a fifth type would appear without a
line of the component changing. The selected type gets a subject field, a
message textarea, the variable reference panel, and a live preview beside them.
Each variable is a button that inserts its placeholder **at the caret** of
whichever field was last focused, so it lands mid-sentence where the name goes.
A badge says *Customized* or *Platform default*; **Reset to platform default**
loads the platform's text back into the editor without writing anything, since
saving is still what writes.

Both composers check the text inline before it is sent, using the server's own
rules: subject and message are required, within `NOTICE_FIELD_LIMITS` (200 and
5,000 characters, from `packages/api/src/lib/notice-field-limits.ts`), and use
only the placeholders that composer supports. A problem is shown under its field
and focus moves to it; the message field also shows a character counter. The
send button is not disabled for missing text — pressing it says what is missing.
A refusal from the server is an inline strip, never a toast.

**General info broadcast.** Recipient select, subject, message, the two-variable
panel and a preview. The recipient select opens unanswered (*Select…*): nothing
is counted and the button reads *Send broadcast* until an audience is chosen,
and pressing it without one puts *Select the recipients.* under the select — so
"every customer" is never an audience nobody chose. Once chosen, the audience
and its size are shown before anything is sent, and the send button itself
reads *Send to N recipients*. Success, delivery
failure, sending and validation each have their own state.

**Repair companies.** Read-only. Company, phone, email and status, with a link
to `/wp/repair-companies` for the management controls — duplicating add, edit
and deactivate here would mean two places to keep in step. The empty state's
call to action is a real `<a>` carrying `buttonVariants` styling rather than
Base UI's `Button` with a link in its `render` prop: that primitive assumes a
native `<button>`, and the `nativeButton={false}` escape hatch silences its
warning by stamping `role="button"` onto the anchor. A control that navigates
should announce as a link and offer middle-click and open-in-new-tab, so the
styling is borrowed and the element is left alone.

For `wp_sub_admin` and `wp_employee` the write controls are not rendered at all
and the fields are disabled, with one sentence saying why: *Your role can read
notice settings. Only a WP Admin can edit a template or send a broadcast.*

Design notes, from the [design system](/docs/design-system): the page title is
the only Sora on the screen, statuses use the success and neutral tint pairs,
and the preview sits in a bordered card at the right on desktop, below the
editor on narrow widths. Colours come from the tokens in
`packages/ui/src/styles/globals.css`.

`npm run test:db` forces `EMAIL_DRIVER=console` for the test process, so the
broadcast suites never attempt live delivery to their fixture customers,
whatever the local environment sets; they still run against the configured
scratch `DATABASE_URL` (see
[Invitations and Onboarding](/docs/invitations-onboarding#tests)).

The two database suites seed two purveyors with deliberately interchangeable
templates and customers — same names, same text — so a leak between them looks
like a leak rather than like a plausible row.

The RLS suite is a separate boundary on purpose. The API suite runs through the
privileged connection, which bypasses RLS entirely, so nothing it asserts says
anything about whether the policies work.
