This page documents the visual language for the real Next.js + Tailwind implementation. It started from the client-approved click-through prototype; the color palette below is the client's pixel-verified theme sheet (cyan-blue primary, cool blue-grey neutrals). Layout and component patterns are unchanged from the original prototype — only the color tokens and typography moved.

The prototype's layout — which screen has which sections, the wizard's step sequence, table/modal/sidebar composition — is kept as a readable reference at `.agents/skills/bfa-design-system/reference/prototype-layout.html`. **Colors and fonts in that file are the original prototype's and are superseded by this page** — use it for structure only, then reskin with the tokens below.

Primary, the neutrals, and the success/danger/warning pairs are the client's pixel-verified theme-sheet values. The secondary teal accent and the AG-rate purple were not on that sheet and are carried over unchanged from the original prototype; keep the "saturated text on a pale tint" pairing if new states are added.

Dark colors never appear as full backgrounds in this system — every accent is a saturated text color paired with a pale tint background (badges, stat-card icon chips). Keep that pairing when adding new states rather than inventing new backgrounds.

## Typography

Two font families, split by role — not by section:

- **Inter** — everything except page-level titles: nav labels, card/section titles ("Pending Invitations", "Users"), body text, table content, buttons, badges, inputs, labels. Weight 400–700 depending on context.
- **Sora** — page-level H1 titles only (e.g. "Invitations & Access"). Weight 600–700. Nothing below that heading tier switches to Sora — a card title sitting right under the page title still renders in Inter.
- Load both via `next/font/google` in the app shell (mirrors how `apps/fumadocs` already loads Inter) — do not self-host or use a CDN `<link>`, per the portability constraints in `bfa-requirements`.
- Body/UI text: 13–14.5px, weight 400–600.
- Section/card headings (Inter): 15.5–20px, weight 700.
- Page title (Sora): 22–28px, weight 700.
- Labels above inputs: 12px, `#687A8D`.
- Badges/pills: 11px, weight 600.
- Letter-spacing `.03–.05em` + uppercase only on small eyebrow labels (section labels, menu group headers).

## Spacing & radius

- Card / table / modal radius: **10–12px**. Buttons and inputs: **8px**. Badges/pills: **6px**.
- Card padding: 16–24px. Table cell padding: `11px 16px`. Input padding: `10px 12px`.
- Card border: `1px solid #E1E6EA` (or `#EEF1F4` for a lighter nested card) plus a subtle shadow `0 1px 2px rgba(27,36,45,0.05)` — never a heavier shadow.
- Gaps between grid items / stat cards: 14–16px.

## Layout shell

- **Certifier (mobile-first):** phone width uses a bottom tab bar (Dashboard / Profile); desktop width (≥780px) switches to the same 216px left sidebar used by WP/Admin. Content max-width `480px` centered on desktop for forms, full-width for tables.
- **WP / Super-Admin (desktop-oriented):** fixed 216px left sidebar (white, `1px solid #E1E6EA` right border), icon + label nav items, active item gets `#D9F0FC` background + `#0E5A81` text/icon. Top header bar (white, bottom border) shows the current WP/company name and a "Switch role" or contextual action on the right.
- **Impersonation banner:** full-width `#FEF3C7` bar above the shell, `#92400E` text, with an underlined "Exit impersonation" link — always visible while impersonating, never folded into a menu.

## Components

**Stat card** — white card, radius 12px, a 3px colored top accent bar (`#1588C1` primary metrics, `#0D9488` secondary/computed metrics, `#DD2C3B` for danger metrics like past-due count), a 32–38px icon chip in the matching tint color, a 12px muted label, and a 24px bold number.

**Table** — header row `#EFF3F5` background with `#E1E6EA` bottom border, 12px/600-weight muted header labels; body rows separated by `#EEF1F4`, hover `#F4FAFD` when the row is clickable (drills into a detail view).

**Badge** — pill, 11px/600 weight, `padding: 3px 9px`, `border-radius: 6px`, colored text on a matching pale tint background per status (see palette table). Never a solid-fill badge.

**Buttons** — primary: `#1588C1` fill, white text, radius 8px, weight 600, hover `#11719E`. Secondary/outline: white fill, `1px solid #D5DBE1` border, same radius/weight. Icon-only segmented control (e.g. sign-off method toggle): pill container `#E7EBEF`, active segment white with subtle shadow.

**Inputs** — `1px solid #D5DBE1`, radius 8px, `10px 12px` padding, 14px text. Read-only/auto-filled fields (e.g. BIN-found assembly details) get a flat `#E7EBEF` background with `#687A8D` text instead of a disabled look.

### Form validation

Every form, dialog and inline editor reports field problems the same way, and
never through the browser's own validation popups or a toast.

- **Pieces.** `useFormValidation` (`packages/ui/src/hooks/use-form-validation.ts`)
  tracks which fields' errors are visible and wires ids; `FieldError`,
  `FormError` and `FieldCounter` (`packages/ui/src/components/field-message.tsx`)
  render them; `DateInput` (typed date plus calendar picker) and `PhoneInput` are
  the date and phone controls; the rules (`required`, `email`, `usPhone`, `usDate`,
  `usDateNotBefore`, `maxLength`, `composeRules`) live in
  `packages/ui/src/lib/validation.ts`.
- **Look.** An invalid control gets the existing `aria-invalid` styling on
  `Input`, `Textarea` and the Base UI `SelectTrigger` (danger border and ring).
  Its message sits directly under the control: 12px danger text with a
  `TriangleAlert` icon. A refusal that belongs to no single field is a
  `FormError` strip (danger tint) above the buttons.
- **Semantics.** Forms set `noValidate` and carry no `required`, `minLength`,
  `maxLength` or `type="date"` constraints. The control points at its message
  with `aria-describedby` (alongside any hint it already had) and the message is
  `role="alert"`.
- **Timing.** Nothing shows when a form opens. Leaving a field that was changed
  reveals its problem; submitting reveals every problem and focuses the first
  invalid control. A revealed message follows the value — it clears on the
  keystroke that fixes it and is never left stale. Missing answers never
  disable the submit button; pressing it explains what is missing.
- **Formats.** Emails need a reasonable address shape (*Please enter a valid
  email address.*). US phones are ten digits, masked as `(XXX) XXX-XXXX` while
  typed (see *Phone mask* below). Dates are `MM/DD/YYYY` — all four year
  digits, a two-digit year is refused rather than guessed — must be real
  calendar days, are rewritten in that exact spelling on blur (`2/3/2027` →
  `02/03/2027`), and are converted to `YYYY-MM-DD` only at the API boundary.
- **Date mask.** `DateInput` masks entry as `MM/DD/YYYY`: only digits are
  accepted from the keyboard and paste, slashes appear after the month and day,
  and the text stops at eight digits (ten characters). Backspace, Delete,
  selection replacement and paste edit the digits and keep the caret where the
  person was working; a pasted `2/3/2027` is padded to `02/03/2027`. The mask
  shapes text only — `02/30/2026` stays as entered and the inline date error
  explains it.
- **Select placeholders.** A select for a value a person must decide — a
  status, a BFA type, a rate category, a broadcast's recipients — opens on
  `SELECT_PLACEHOLDER` (*Select…*, from `packages/ui/src/components/select.tsx`)
  rather than on its first option, and a `required` rule reports *Select a …*
  under it with the same `aria-invalid`/`aria-describedby` wiring. Editing an
  existing record keeps its stored value selected. A deliberate "no value"
  answer stays a real option where the business allows it (*No customer yet*,
  *Not recorded*), and list filters keep their *All …* default. Forms convert to
  a payload only from completed values, so `""` never reaches an API enum.
- **Unique fields.** A uniqueness rule lives in the database (a unique index),
  never only in a pre-check. The procedure catches that specific violation and
  answers `CONFLICT`; the form routes `CONFLICT` to the field it belongs to
  (duplicate BIN → BIN, duplicate email → Email) and clears the message once
  that field's value changes.
- **Phone mask.** `PhoneInput` masks entry as `(XXX) XXX-XXXX` on the same
  digit-mask model (`packages/ui/src/lib/digit-mask.ts`): only digits from the
  keyboard or paste, separators added as each group completes, at most ten
  digits, with Backspace, Delete, selection replacement and the caret behaving
  as for dates. A pasted or autofilled `5551234567` or `+1 555 123 4567` becomes
  `(555) 123-4567`; a paste that would exceed ten digits is refused rather than
  cut down. Pasted or autofilled text is held to the server's character rule:
  anything with a letter, an extension (`x12`, `ext. 12`), another character or
  a `+` that is not the `+1` country code (`+5551234567`, `+2 …`, `+44 …`) is refused whole and the field is
  left unchanged — forbidden characters are never stripped into a valid number. An incomplete number stays as entered with the inline phone error.
  Only phone fields are masked — email and address fields stay free text with
  their existing inline rules.
- **Date picker.** `DateInput` pairs the typed field with a calendar button
  (Base UI `Popover`, no extra dependency) following the WAI-ARIA date picker
  dialog pattern: the button and dialog are named by `pickerLabel` (for example
  *Choose annual test date*); focus opens on the selected day or today; the
  days are a grid with a roving tab stop — arrows move by day or week,
  Home/End to the week's ends, Page Up/Down by month (Shift for a year), Enter
  or Space chooses; Escape or choosing a day closes it and returns focus to the
  button. Choosing a day writes `MM/DD/YYYY` into the field. Day arithmetic uses
  UTC fields only, so no day shifts across time zones. Length limits
  come from the same constants the Zod schemas use; long-text fields (notice and
  broadcast messages) also show a character counter.
- **Server errors.** Still the boundary. A refusal that maps reliably to one
  field (a duplicate BIN) is shown at that field; anything else is a
  `FormError`. Toasts are for successful operations and for row actions with no
  form to report into.

**Modal** — centered, white, radius 12px, `24px` padding, backdrop `rgba(16,24,40,0.45)`. Click-outside-to-close via a backdrop click handler that stops propagation from the modal body.

**Wizard progress** — a row of thin (5px) rounded segments, one per step, filled `#1588C1` up to the current step, `0.5` opacity for the remainder. Step label underneath in 12px muted text ("Step 3 of 6 · Test readings").

**Icons** — [Lucide](https://lucide.dev)-style stroke icons only (no filled icons), stroke-width 1.6–2.2, sized 14–26px depending on context. Never mix in a different icon family.

## Applying this system in the real app

The shared UI primitives live in `packages/ui` (shadcn/ui). When implementing a screen from the [PRD](/docs/prd):

1. Map the token table above onto Tailwind theme values / CSS variables in `packages/ui/src/styles/globals.css` rather than hardcoding hex values in components.
2. Reuse the shadcn primitives (`Button`, `Badge`, `Card`, `Table`, `Dialog`) and restyle them to match these tokens once, instead of re-deriving the look per screen.
3. Where the prototype and a shadcn default disagree (e.g. badge padding, card radius), the prototype wins — it's what the client has already seen and approved.
