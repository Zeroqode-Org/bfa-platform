There is no sign-up form. Every account on this platform exists because somebody
was invited and redeemed a link, which is what makes the tenant model hold: the
role and the water purveyor are decided by the inviter, server-side, before the
invitee ever types anything.

This page describes the flow as built. It covers *Invitations and onboarding* in
the [build plan](/docs/build-plan) and the send helper and drivers of
*Transactional email integration*.

## The flow end to end

1. A Super-Admin or any WP role calls the `invitations.createInvitation`
   procedure — from the invite-new-WP dialog on `/admin`, or directly. The
   procedure decides which purveyor the invitation belongs to from the caller's
   own profile — never from the request body.
2. A 256-bit secret is generated. Its SHA-256 digest is stored in
   `invitations.token`; the secret itself only ever appears in the email.
3. The email goes out through the shared send helper. Under the default
   console driver it prints the whole message — invite link included — as one
   JSON log line; with `EMAIL_DRIVER=provider` it is delivered through Resend.
4. The invitee opens `/invite/<secret>`. The page resolves the token
   server-side and renders the right form for the invitation.
5. Submitting the form runs the `redeemInvitation` server action: it creates the
   `auth.users` record, then writes every `public` row in one transaction, and
   marks the invitation redeemed.
6. The invitee is signed in and lands on their dashboard.

## Where people land

`/` renders nothing. It resolves the caller's `profiles` row and forwards them:

| Role | Lands on |
|---|---|
| `super_admin` | `/admin` |
| `wp_admin`, `wp_sub_admin`, `wp_employee` | `/wp` |
| `certifier` | `/certifier/drafts` |
| not signed in | `/login` |

The table lives in `apps/web/src/lib/landing-route.ts` and has three readers —
this redirect, the invite-redemption action, and the role gate that bounces
somebody out of a section they cannot see. One table, because three copies of
the same switch is three chances to send a role somewhere it will be turned
away from.

This replaced the workspace picker, a development shortcut that asked people
which role they were and let anyone walk into any of the three shells. Roles are
resolved server-side now, so asking was both pointless and misleading — the
sections enforce the answer regardless of which card was clicked.

`/` itself stays as the redirect hub rather than being deleted: it is where the
sign-in screen sends people, what the sidebar logo links to, and the only place
that knows a role without being told one.

## Sending an invitation

`packages/api/src/routers/invitations.ts`

```ts
// Into an existing purveyor — the caller's own, decided server-side.
await trpc.invitations.createInvitation.mutate({
  email: "certifier@example.com",
  role: "certifier",
  expiresInDays: 7,
});

// Provisioning a new purveyor. Super-Admin only; this is what the
// invite-new-WP dialog sends.
await trpc.invitations.createInvitation.mutate({
  email: "admin@riversidewater.gov",
  role: "wp_admin",
  waterPurveyorId: null,
  proposedWaterPurveyorName: "Riverside Water District",
});
```

**Who may invite whom** — decided by `resolveInvitationTarget` in
`packages/api/src/lib/invitations.ts`, and enforced a second time by the row
policies:

| Caller | May invite | Into which purveyor |
|---|---|---|
| Super-Admin | any role | any purveyor, or none — a null `associated_wp_id` provisions a new one |
| WP Admin | any role | their own, only |
| WP SubAdmin | any role | their own, only |
| WP Employee | any role | their own, only |
| Certifier | nothing | — |

A WP role that passes a `waterPurveyorId` other than their own gets a
`FORBIDDEN`, not a silently rewritten row: a cross-tenant attempt should be
visible in the logs, not absorbed.

Two combinations are rejected as `BAD_REQUEST`, because they describe an
invitation nothing could redeem: a null purveyor with any role but `wp_admin`
(only a first administrator brings a purveyor into existence), and a certifier
invitation with no purveyor to authorize against.

### Inviting a new water purveyor

`apps/web/src/components/admin/invite-wp-dialog.tsx`

The Super-Admin names the purveyor and gives the address of its first
administrator. The invitation is stored with `associated_wp_id` null and the
name in `proposed_water_purveyor_name`; redeeming it creates the
`water_purveyors` row and that administrator's profile in one transaction.

**The name is collected once, by the Super-Admin.** It travels on the
invitation, so the person redeeming the link is shown the name rather than asked
for it — nobody is invited to name an organisation that has already been named
for them, and two people cannot disagree about what it is called.

Three layers keep this to the Super-Admin, and they are independent:

1. `/admin` is gated to `super_admin` in its layout, so the button is not
   reachable by anyone else. A hidden button is not a permission, which is why
   it is the weakest of the three.
2. `resolveInvitationTarget` refuses a null purveyor, and refuses a
   `proposedWaterPurveyorName` at all, for every role but Super-Admin —
   `FORBIDDEN`, not a silently dropped field.
3. A check constraint, `invitations_new_wp_name_shape`, refuses any row where
   the two do not agree: a name is present exactly on a `wp_admin` invitation
   with no purveyor, and absent on every other kind.

The confirmation reports the actual user-facing delivery outcome without
exposing a driver name: after Resend accepts a message it says an invitation
email was sent; under the console driver it says email delivery is not enabled
and the invite link is in the server log. The response exposes only `sent` or
`logged`, never the server configuration or credentials.

### Tokens

The stored token is **not** a UUID and **not** the value in the link.

- The link carries 32 bytes from `randomBytes`, base64url-encoded.
- `invitations.token` holds the SHA-256 digest of that secret, lowercase hex.
- Redemption hashes the incoming secret and looks the digest up on the unique
  index — one indexed equality match, no scan.

A dump of the `invitations` table therefore yields nothing anyone can redeem.
SHA-256 is FIPS-approved, which the project's crypto rule requires; a UUID would
not be, and a UUID is an identifier rather than a credential in any case.

Invitations expire seven days after creation unless the caller passes
`expiresInDays` (1–30).

## The email layer

`packages/api/src/lib/email.ts` is the only place this application sends mail
from. Feature code calls `sendEmail(message, context)` and never touches a
provider SDK, and never writes its own send log.

```ts
type EmailMessage = { to: string; subject: string; html: string; tags: EmailTag[] };
type EmailDriver = { name: EmailDriverName; send(message: EmailMessage): Promise<EmailSendResult> };
```

Two drivers are registered, and `EMAIL_DRIVER` picks one. Nothing else in the
application knows which is running.

**`consoleDriver`** — the default. It logs the complete payload, including the
rendered HTML, and reports success. The HTML is logged in full deliberately:
wherever the provider is not switched on, that log line is the only copy of the
invite link a developer or tester has.

```json
{"event":"email_console_delivery","driver":"console","email_id":"console_…","to":"certifier@example.com","subject":"You have been invited to the Backflow Assembly platform","tags":[{"name":"type","value":"invitation"}],"html":"<!DOCTYPE html>…<a href=\"http://localhost:3001/invite/HqA…\" style=\"…\">Set up your account</a>…","timestamp":"2026-09-09T09:35:45.931Z"}
```

**Every send attempt** also emits one `email_send_attempted` line, whichever
driver ran and whether it succeeded or threw, carrying the event type, the
recipient, a timestamp, and whichever context identifiers the caller knew:

```json
{"event":"email_send_attempted","email_event":"invitation_created","driver":"console","status":"sent","email_id":"console_…","error":null,"recipient":"certifier@example.com","subject":"…","actor_id":"…","recipient_id":null,"wp_id":"…","asset_id":null,"invitation_id":"…","timestamp":"…"}
```

**`providerDriver`** — delivers through [Resend](https://resend.com), using the
official `resend` SDK from inside `email.ts` and nowhere else. The account
exists and the sender domain `backflowreporter.io` is verified. Each send maps
the message straight across:

| Resend field | Comes from |
|---|---|
| `from` | `RESEND_FROM_EMAIL` |
| `replyTo` | `RESEND_REPLY_TO` |
| `to`, `subject`, `html`, `tags` | the `EmailMessage` fields of the same name |

**Reply-To.** Every message sent through Resend carries `Reply-To:` set to
`RESEND_REPLY_TO` — in production, `info@backflowreporter.io`. The sending
address is not a mailbox anyone reads, so without it a recipient who answers an
invitation or a notice would be writing to nobody. With it, the reply goes
straight to the existing monitored inbox; the platform receives nothing.
Resend inbound receiving and webhooks are **not** used. The address is provider
configuration, not message data: `EmailMessage` has no reply field and no call
site chooses one, so every transactional email replies to the same place.

Resend's email id is returned as the send's `id`, so it is the `email_id` in the
`email_send_attempted` line. The provider driver writes no payload log of its
own — the message is in Resend, not in the server console.

Resend reports a refused send as an error value rather than by throwing. The
driver turns that, and a response with no id, into a thrown error, so
`sendEmail` logs `status: "failed"` with the message and the caller's
behaviour is unchanged: an invitation whose email was refused fails instead of
reporting a success nobody received.

Adding the provider changed no call site: it is one entry in the `drivers`
registry in `email.ts`, which is what the build plan means by "no code edit
outside `email.ts`".

### Configuration

| Variable | Required | Default | Purpose |
|---|---|---|---|
| `EMAIL_DRIVER` | no | `console` | Which driver `sendEmail` uses: `console` or `provider` |
| `RESEND_API_KEY` | when `EMAIL_DRIVER=provider` | — | Resend API key (`re_…`). Server-only secret |
| `RESEND_FROM_EMAIL` | when `EMAIL_DRIVER=provider` | — | Sender, as `address@domain` or `Display Name <address@domain>` on a verified domain |
| `RESEND_REPLY_TO` | when `EMAIL_DRIVER=provider` | — | Plain email address replies are sent to — `info@backflowreporter.io` in production |
| `APP_URL` | no | — | Explicit base URL for links in outbound mail. Portable override for Docker, any other host, or a Vercel project that needs a different domain |
| `NEXT_PUBLIC_APP_URL` | no | — | **Legacy.** Kept temporarily for backward compatibility; used when `APP_URL` is not set. Do not use in new configuration |
| `VERCEL_PROJECT_PRODUCTION_URL` | no | — | Set by Vercel itself. Used when neither `APP_URL` nor `NEXT_PUBLIC_APP_URL` is set |

The email variables and both URL variables are validated in
`packages/env/src/server.ts`.
**Console remains the default**, and it needs neither Resend variable, so CI, a
fresh clone and every environment that has not opted in keep working with none
of them set. Real delivery happens **only** where `EMAIL_DRIVER=provider` is set
explicitly.

When it is, all three Resend variables become required: a missing key, a key
without the `re_` prefix, a malformed sender, or a reply-to that is not a plain
email address fails env validation at startup, before any request is made. The
driver checks for all three again before building the client, so a run with
`SKIP_ENV_VALIDATION` still fails with a clear message rather than a request.

The Resend variables never take a `NEXT_PUBLIC_` prefix — they are read only by
server code and must not reach a browser bundle. Locally they live in
`apps/web/.env.local`; in a deployment they are set as environment variables.
`EMAIL_DRIVER=provider` is not set in any deployment yet.

### Links in outbound mail

`packages/env/src/app-url.ts` — `resolveAppBaseUrl`, called by `appBaseUrl()`
and `buildInviteLink()` in `packages/api/src/lib/invitation-token.ts`.

Every link in an email is an absolute `http(s)` URL built on one base URL,
chosen from configuration in this order:

1. **`APP_URL`**, when set. The explicit, portable override — use it for Docker
   and every host other than Vercel, or on Vercel to pin a domain other than the
   project's production one.
2. **`NEXT_PUBLIC_APP_URL`**, when `APP_URL` is not set — **legacy**, kept
   temporarily so environments that already set it keep their links. New
   configuration should set only `APP_URL`; this fallback will be removed once
   existing environments have moved over.
3. **`VERCEL_PROJECT_PRODUCTION_URL`**, when neither of the above is set. Vercel
   provides it as a bare hostname, so `https://` is prepended. It is the
   project's production domain, which is why a domain change reaches the links
   without anyone editing a variable.
4. **`http://localhost:3001`**, only when none is set — a fresh clone, tests
   and CI. The port is `apps/web`'s dev server.

An empty value counts as unset. A trailing `/` is dropped, so a base of
`https://app.example.com/` still yields `https://app.example.com/invite/…`.

**A value that is set but invalid stops the app** rather than falling through to
the next source. `APP_URL` (and the legacy `NEXT_PUBLIC_APP_URL`, under the same
rules) must be an absolute `http:` or `https:` URL with a hostname and no
credentials, query string or fragment — `javascript:`, a
relative path or a bare hostname are refused. `VERCEL_PROJECT_PRODUCTION_URL`
must be a bare hostname, as Vercel sends it. Both are checked by env validation
at startup, and again every time a link is built, so a `SKIP_ENV_VALIDATION`
run throws before a send instead of mailing a bad link.

Two sources are **deliberately not used**:

- **`VERCEL_URL`** — the URL of one specific deployment, previews included. A
  link to it can land a recipient on a stale build or behind Vercel's
  deployment protection.
- **Request headers** — `Host` and `X-Forwarded-Host` are chosen by whoever sends
  the request, so building a link from them is a host-header injection, and
  background jobs have no request to read.

`NEXT_PUBLIC_APP_URL` is read only from the server's environment, for backward
compatibility. This is server-only configuration and nothing in a browser
bundle needs it, so when touching an environment, move the value to `APP_URL`.

**Vercel setup.** Vercel only passes `VERCEL_PROJECT_PRODUCTION_URL` to the app
when the project exposes its system variables: in the Vercel Dashboard, open
the project's **Settings → Environment Variables** and enable **Automatically
expose System Environment Variables**, then redeploy production. Without that
setting, and without `APP_URL` or `NEXT_PUBLIC_APP_URL`, a Vercel deployment falls back to localhost
links. The code uses no Vercel runtime API: the variable is read like any other.

### The shared email layout

Every message the application sends is a complete HTML document rendered by
`packages/api/src/lib/email-layout.ts`. Feature code builds a **safe body
fragment**, the layout wraps it, and the finished string goes into
`EmailMessage.html`. `email.ts` is untouched by any of this: it still delivers
`{ to, subject, html, tags }` and does not know how the HTML was made, so the
console driver logs, and Resend receives, exactly the same document.

The shell is one layout for every message:

| Part | What it is |
|---|---|
| Header | The wordmark **Backflow Assembly Platform**, as text |
| Body | A white card, 600px wide at most and fluid below that, with a thin blue top bar; the message's `<h1>` when it has one, then the body fragment |
| Footer | One line: *Sent through Backflow Assembly Platform.* |

It is written for email clients rather than browsers:

- **Table-based outer layout with inline styles** on every element that carries
  a visual rule. A small `<style>` block adds narrow-screen padding and paragraph
  spacing for clients that honour it; nothing depends on it. Outlook gets a
  fixed 600px conditional table.
- **Nothing remote.** No images, no web fonts, no stylesheets, no tracking pixels
  and no rewritten links — a system font stack and literal design-system
  colours. The layout adds no tracking of its own; open and click tracking must
  also stay **off** in the Resend domain settings, which this code cannot see.
- **Text-only branding, deliberately.** There is no logo in the message and none
  was invented: the brand is the words "Backflow Assembly Platform" until the client
  supplies a logo asset they own. Nothing in any message is carried by an image.
- **Accessible.** `lang="en"`, the subject as the document title and the
  message's accessible name, at most one `<h1>`, and a CTA whose link text says
  what it does. The button fill is the primary hover shade `#11719E` rather than
  `#1588C1`, because white on the brighter blue is roughly 3.9:1 and fails WCAG
  AA for body-size text; `#11719E` is roughly 5.4:1. Footer and helper text use
  a darkened secondary for the same reason.

**Escaping.** `renderEmailLayout` escapes the title and heading itself and
inserts `bodyHtml` as given, so a body fragment must already be safe — the
output of `templateToHtml`, or markup built from `escapeHtml` and the layout's
helpers. Link targets go through `emailHref`, which accepts only absolute
`http:` / `https:` URLs and escapes them for the attribute; anything else throws
before a send is attempted.

**The invitation email** is `renderInvitationEmail` in
`packages/api/src/lib/invitations.ts`, a pure function `sendInvitationEmail`
calls before `sendEmail`:

1. `<h1>` *You have been invited*.
2. Who invited them into what, as which role — the purveyor name escaped.
3. A button labelled **Set up your account**.
4. The same invite URL as visible link text, under *If the button does not work,
   copy and paste this link into your browser:*.
5. The expiry, written for a reader in UTC — *June 8, 2026 at 3:30 PM UTC*.
6. A muted line saying an unexpected invitation can be ignored.

The subject is unchanged. Plain-text messages — general-info broadcasts now,
automated notices once Workflow 1 sends them — use `renderTextEmail` instead;
see [WP Notices & Email](/docs/wp-notices#the-email-shell).

## Row-level security

Migration `0001_invitation_onboarding_policies`. The
`proposed_water_purveyor_name` column and its check constraint arrive separately
in `0002_invitation_proposed_wp_name` — one migration per change, so neither has
to be edited after the fact.

Every policy resolves the caller through their own `profiles` row. Reading
`profiles` from inside a policy *on* `profiles` recurses, so the lookup lives in
two `SECURITY DEFINER` helpers in a `private` schema, which PostgREST does not
expose:

- `private.current_global_role()`
- `private.current_wp_id()`

They read nothing but the caller's own row — there is no argument to point them
at somebody else — and a **blocked** profile resolves to `NULL`, so a blocked
user keeps only the `id = auth.uid()` paths and loses every role- or tenant-wide
grant.

### `invitations`

| Role | Select | Insert | Update / delete |
|---|---|---|---|
| Super-Admin | all | all, including a null `associated_wp_id` | yes |
| WP Admin / SubAdmin / Employee | own purveyor | own purveyor, `associated_wp_id` not null | no |
| Certifier | — | — | — |

The `associated_wp_id IS NOT NULL` clause in the WP insert policy is what keeps
new-purveyor provisioning exclusive to the Super-Admin.

Redemption never reads through these policies: it runs in a server action with
the privileged connection, so tokens are not enumerable from a client.

### `profiles`

| Role | Select | Update | Insert |
|---|---|---|---|
| Any authenticated user | own row | own row | — |
| WP Admin / SubAdmin | own purveyor | — | — |
| Super-Admin | all | — | — |

Two details worth knowing:

- **The update is column-limited, not just row-limited.** A row policy cannot
  stop a user from writing their own `global_role`, `water_purveyor_id` or
  `status`; a column grant can, so `authenticated` holds `UPDATE (full_name)`
  and nothing more. Attempting anything else is a `permission denied`, not a
  silent no-op.
- **There is no INSERT policy and no INSERT grant.** Profiles are created by the
  redemption path with the service-role key, which bypasses RLS. Anything else
  creating a profile is a bug, and the missing policy is what makes it fail
  loudly.

Super-Admin writes to either table run through the privileged server connection
behind `superAdminProcedure`, the same way `listWaterPurveyors` already does.

## Redemption

`packages/api/src/lib/invitation-redemption.ts`, called by the server action in
`apps/web/src/app/invite/[token]/actions.ts`.

`inspectInvitation` resolves a token to one of six states. Reads only — an
invitation is not consumed by being looked at, so a refreshed page or a link
opened twice before submitting still works.

| State | What the invitee sees |
|---|---|
| `not_found` | "This invitation link is not valid. Check that you copied the whole link." |
| `expired` | "This invitation has expired. Ask whoever invited you to send a new one." |
| `redeemed` | "This invitation has already been used. Sign in with the account it created." |
| `revoked` | "This invitation is no longer valid…" |
| `email_in_use` | "An account already exists for this email address. Sign in instead." |
| `valid` | the first-login form, in one of three shapes |

`is_redeemed` and `status` are checked separately even though redemption writes
both: they are two columns that can drift, and a token that is redeemed by one
measure and pending by the other must not be usable.

### The three redemption modes

| Mode | When | What the form asks for |
|---|---|---|
| `new_profile` | the ordinary case | full name, password; plus company, ID number and license expiration date for a certifier |
| `new_water_purveyor` | `associated_wp_id` is null | the same as above — the purveyor's name came with the invitation and is shown, not asked for |
| `existing_certifier` | the address already belongs to a certifier | nothing — one confirm button |

The form checks its fields inline before the server action runs (the shared
[inline validation](/docs/design-system#form-validation) pattern): every
requested field is required, the password needs at least 8 characters and a
matching confirmation, and the license expiration date is typed as `MM/DD/YYYY` or chosen from the calendar picker,
must be a real calendar day, and is posted to the action as `YYYY-MM-DD`. A
form that fails those checks never reaches the action; one that passes them and
is still refused shows the action's message inline, never as a toast.

The mode is decided on the server from the invitation itself and passed into the
form, so a tampered form cannot ask for a different set of fields than the
invitation calls for. The action revalidates all of it regardless.

### Atomicity

Two stores are written and they cannot share a transaction — `auth.users` lives
behind Supabase's Auth API. The order is chosen so that a failure never leaves a
usable half-account:

1. The `auth.users` record is created first, outside the transaction, so the
   transaction holds no row lock across a network call.
2. One transaction then does everything else. Its **first** write is a
   conditional claim on the invitation (`is_redeemed = false AND status =
   'pending' AND expires_at > now()`), so two redemptions racing on the same
   link cannot both proceed — the loser matches no row and rolls back.
3. If the transaction rolls back, the auth user is deleted. Otherwise the
   address could never redeem a replacement invitation.

The reverse order would strand a profile with no way to sign in, which no
compensating write could clean up as safely.

### Second-WP path for an existing certifier

A certifier already on the platform who is invited by a second purveyor keeps
everything they have. Their `profiles` row and their `certifiers` row are not
read-modify-written at all; only a `wp_certifier_authorizations` row is inserted,
with `on conflict do nothing` so a duplicate invitation for a purveyor they
already serve is a no-op rather than a constraint failure.

They are never shown a profile form. If they have a live session they go
straight to their dashboard; otherwise they are sent to `/login?redirect=…`,
which the sign-in screen honours for same-origin paths only.

An address that already belongs to a **non**-certifier gets `email_in_use`
instead — extending that account would mean rewriting a profile somebody is
already using.

## Structured logging

Every event below is one `console.log(JSON.stringify(…))` line.

| Event | Emitted by | Carries |
|---|---|---|
| `invitation_created` | `createInvitation` | actor, invitation id, recipient, role, wp id, expiry |
| `email_send_attempted` | `sendEmail` | event type, driver, status, recipient, actor / wp / asset / invitation ids |
| `email_console_delivery` | `consoleDriver` only | the full payload, including the invite link |
| `invitation_redeemed` | `redeemInvitation` | actor, invitation id, mode, role, wp id |
| `invitation_redemption_failed` | `redeemInvitation` | invitation id, mode, reason |
| `invitation_redemption_cleanup_failed` | `redeemInvitation` | the orphaned auth user id, if its deletion failed too |

## Trying it locally

```bash
npm run db:migrate
npm run db:seed
npm run dev:web
```

Sign in as a seeded WP Admin, call `invitations.createInvitation`, and take the
`html` field out of the `email_console_delivery` line in the server console. The
`/invite/<secret>` URL in it is a working link. Leave `EMAIL_DRIVER` unset for
this: local development uses the console driver even when Resend credentials
are present in `.env.local`, so nothing is emailed by accident.

## Tests

```bash
npm test
```

runs the unit suites only — no network, no database, and no read of anybody's
credentials file. That is the run to expect on a fresh clone and in CI.

```bash
npm run test:db
```

adds the database-backed suites — and runs them **only against
`TEST_DATABASE_URL`**, a dedicated, disposable database. The runner
(`scripts/run-db-tests.mjs`) refuses to start when the variable is unset, and
refuses a URL that names the same database as the development `DATABASE_URL`;
the development URL is never used as a fallback and is never connected to by
a test run. The reasoning, and how the runner bootstraps and migrates a bare
target on its own, is written up on
[Database Baseline & Test Isolation](/docs/database-baseline). Set
`TEST_DATABASE_URL` in the shell or in `apps/web/.env.local` — only that one
key is read from the file for the test connection; the rest of the file is
still loaded under `RUN_DB_TESTS=1` for the auxiliary variables env
validation requires, and nothing in it can redirect the run.

The runner also pins the child environment: `EMAIL_DRIVER=console`, because
the suites send invitations and broadcasts to fixture addresses such as
`@example.com` and a developer's local `EMAIL_DRIVER=provider` would hand
them to Resend, which attempts real delivery and rejects those recipients;
and `SCHEDULER_ENABLED=false`, so no test process ever starts a tick loop.
Both apply to `npm run test:db` only; the app and production read their
configuration as set.

Arguments pass through, so `npm run test:db -- rls` runs just the RLS suite.
Each suite cleans up its own fixtures; the RLS suite additionally rolls back
every statement it makes, so nothing it does survives itself.

| File | Opt-in | Covers |
|---|---|---|
| `packages/db/src/rls.test.ts` | yes | the policies as the `authenticated` role, with `request.jwt.claims` set — cross-tenant reads and writes on both tables, certifier exclusion, blocked profiles, the column-grant limit on `profiles` |
