Working document for two developers (Lina, Daniil) and for AI-assisted coding. Every feature below is written to be executable without further clarification: exact file paths, route names, component names, and a testable definition of done.

Read this together with the design system page before writing any UI, and with the `bfa-requirements` skill before adding any dependency, scheduler, or PDF code.

## Ground rules

**Non-negotiables:**

- Every new table gets `ENABLE ROW LEVEL SECURITY` in the same migration that creates it. Policies land in a later migration, per feature.
- No Vercel Cron, KV, Blob, Postgres, or Edge Runtime. Background jobs use the Node-native scheduler.
- All config from env vars. Never hardcoded, never committed.
- Auth events and sensitive row writes emit `console.log(JSON.stringify({ event, actor_id, target_id, timestamp }))` — structured, not a plain string.
- Crypto/token/auth dependencies must use FIPS-compatible algorithms (AES-256, SHA-256). Flag MD5/SHA-1/DES for review before adding.
- Docs update ships in the same PR as the code change.

**Conventions to apply without being asked:**

- **Validation.** Every tRPC procedure input is a Zod schema. No untyped `any` crossing a procedure boundary.
- **Pagination.** Every list procedure takes `{ limit, cursor }` and returns `{ items, nextCursor }`. Cursor-based, not offset. Default limit 25, max 100.
- **Timezone.** Every date the business cares about — `annual_test_date`, notice due dates, AG renewal — is evaluated in **Pacific/Honolulu**, not the server's local time and not UTC. Store `timestamptz`, compute due dates and scheduler windows against that zone explicitly. Getting this wrong sends notices on the wrong day.
- **Errors.** Procedures throw typed `TRPCError` with a proper code (`UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `BAD_REQUEST`). Never return `null` to signal a permission failure — that hides RLS bugs behind an empty state.
- **Money and measurements.** No floats for meter readings. Store as text or numeric with an explicit scale.

## Per-feature workflow

Run this for every feature below, without exception.

```bash
git checkout main
git pull origin main
git checkout -b feature/<short-slug>
```

1. **Migration first** (if the feature needs schema or policy changes). One migration per feature. Edit the schema in `packages/db/src/schema/*.ts`, run `npm run db:generate` (drizzle-kit), hand-add any `ENABLE ROW LEVEL SECURITY` / `CREATE POLICY` SQL the schema DSL can't express to the generated file, then `npm run db:migrate` and verify in the Supabase dashboard before writing app code.
2. **Backend** — tRPC procedures in `packages/api`. Every procedure that touches tenant data must resolve the caller's `profiles` row server-side; never accept `water_purveyor_id` from the client as an authorization input.
3. **Frontend** — components in `apps/web`, built from `packages/ui` primitives. Map design tokens to CSS variables once in `packages/ui/src/styles/globals.css`; never hardcode hex values in a component.
4. **Docs** — update the relevant page in `apps/fumadocs/content/docs/` if behavior changed.
5. **PR** — title it with the feature name, assign the other developer as reviewer, squash merge after approval.

**Definition of done (every feature):**

- Works end-to-end against real data, not seed data only.
- If RLS-backed tables were touched: seed two water purveyors, log in as each, confirm zero cross-tenant reads and zero cross-tenant writes.
- `npm run check-types` passes. Biome clean.
- Docs updated in the same PR.
- Reviewed and approved by the other developer.

# Part 1 — Database

Build the whole schema in one migration, then layer policies per feature. Thirteen tables, created in FK order.

## Shared conventions

- Primary keys: `uuid`, default `gen_random_uuid()`.
- Timestamps: `created_at`, `updated_at` as `timestamptz`, default `now()`.
- Enums: declare once as Postgres enums, reuse across tables. Do not redeclare per column.
- `updated_at` is maintained by a single shared trigger function, applied to every table that has the column. Do not rely on the application to set it.
- Every policy resolves the caller through their own `profiles` row via `auth.uid()`, reading `global_role` and `water_purveyor_id` from it.

**Indexes to create in the same migration.** RLS policies filter on these columns on every single query — without indexes the whole app degrades as soon as there is real data:

- `water_purveyor_id` on `profiles`, `customers`, `bfa_assets`, `repair_companies`, `test_submissions`, `wp_certifier_authorizations`, `notice_templates`, `wp_feature_flags`, `scheduled_jobs`.
- (`water_purveyor_id`, `bin`) unique on `bfa_assets` — doubles as the BIN lookup index.
- (`certifier_id`, `status`) on `test_submissions` — the certifier dashboard's two queries.
- (`bfa_asset_id`, `end_date`) on `customer_assignments` — resolving the current occupant.
- (`status`, `run_at`) on `scheduled_jobs` — the scheduler's claim query.
- (`water_purveyor_id`, `notice_type`) unique on `notice_templates`.
- (`water_purveyor_id`, `feature`) unique on `wp_feature_flags`.
- `token` unique on `invitations`.

**Roles:** `super_admin`, `wp_admin`, `wp_sub_admin`, `wp_employee`, `certifier`.

**Two things row-level RLS cannot express on its own** — enforce these in the tRPC procedure layer, on top of the row policy:

- Column-level write limits (e.g. a WP may update only `certifiers.status`, not the whole row).
- Cross-role visibility that needs a join rather than a flat `water_purveyor_id = mine` check.

### Seed and fixture data

**Owner:** Daniil.
**Week 1** · 3h, folded into the schema budget.
**Prerequisite:** schema migration applied.
**Blocks:** every isolation check and every feature scheduled ahead of its data.

Half the definitions of done in this plan say "seed two water purveyors" or "build against seed data". That script has to exist, and it has to be the same script for both developers, or the two of you will be testing against different worlds.

1. Write `packages/db/src/seed.ts`, runnable with `npm run db:seed`, idempotent — safe to run twice.
2. Seed two complete water purveyors with deliberately similar-looking data (same customer names, overlapping BINs across the two WPs). Similar data is what makes a cross-tenant leak visible instead of plausible.
3. Per WP: one WP Admin, one WP Employee, two customers (one standard, one agricultural with a renewal date), three BFA assets covering different types and different `annual_test_date` values — one past due, one due soon, one comfortably current.
4. Two certifiers: one authorized for a single WP, one authorized for both — the second is what proves the WP selector works.
5. A handful of `test_submissions`: drafts at various `current_step` values, submitted passes, and one submitted fail — enough for the certifier dashboard, submitted-tests view, and analytics to render before the wizard exists.
6. Notice templates: customize one or two types for the first WP, leave the second WP with none — that difference is what proves the platform-default fallback works.
7. Feature flags: switch `automated_notices` on for the first WP, leave the second with no rows at all — that difference is what proves the default-off behaviour and the flag check in the workflows.
8. Print the seeded login credentials at the end of the run.

**Done when:** a fresh developer can clone, migrate, seed, and log in as any of the six seeded users without asking anyone for credentials.

### Node-native scheduler

**Week 5** · 5h. Must land before workflows 1–3, which run in the same week.
**Prerequisite:** the schema, including `scheduled_jobs`.
**Blocks:** the reminder, failure, and AG renewal workflows.

1. Scheduler module in `packages/api/src/scheduler/` — a tick loop that claims due jobs by updating `status` from `pending` to `running` with a conditional write, so two processes cannot claim the same row.

### Answered, for the record

So the answers do not get relitigated when someone rereads an older document:

- **Sign-off** — the property owner signs on the phone; the certifier ticks a bypass checkbox only when the owner is absent, which carries the mandatory disclaimer. A certifier may also leave the test in draft and collect the signature later.
- **A mid-wizard failure never ends the wizard.** The remaining fields are still collected. The failure email fires only on submit — a failed draft sends nothing.
- **The results document is per BFA type**, matching the test actually performed.
- **A WP may correct any data it owns**, including reassigning a BIN and editing a submitted test. A certifier may not: once submitted, they must file a new test instead.
- **All three WP roles can invite certifiers.**
- **A certifier invited by a second WP** gets a normal invite email and skips profile setup on redemption.
- **The AG renewal date does not auto-advance** after the notice sends. Missing it means reapplying.
- **The fail list has no waiting period** — an asset lands on it the moment a failed test is submitted, and leaves when a passing test arrives.
- **Optional features are switched per WP by the Super-Admin**, default off, with no billing logic in the app — pricing is handled outside it.
- **No audit-log UI in v1.** Structured JSON logging still happens on every sensitive write, so the data exists if a visible activity feed is added later.
