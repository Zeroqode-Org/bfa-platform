This page describes the automated notice pipeline as built. It covers the
[build plan](/docs/build-plan)'s *Node-native scheduler*, *Workflow — reminder
and escalating late notices*, and the delivery half of *Workflow — failure
notice and fail list* ([the fail list itself is on the dashboard
page](/docs/wp-dashboard#the-fail-list)), and PRD § 6.7.

The pipeline replaces the water purveyor's paper-mail process with four emails
derived from one field:

| Stage | When it is due | What it carries |
|---|---|---|
| `reminder` | two calendar months before `bfa_assets.annual_test_date` | the notice text, plus the list of testers the customer can call |
| `late_notice_1` | the due date **+ 1 day** | the notice text |
| `late_notice_2` | the due date **+ 32 days** (31 after late notice 1) | the notice text |
| `final_notice` | the due date **+ 63 days** (31 after late notice 2) | the notice text |

A passing test submitted for the assembly ends the chain wherever it has got to.

## One field drives everything

`bfa_assets.annual_test_date` is the sole scheduling source. The purveyor sets
it when it assigns the BIN ([WP BFA Assets](/docs/wp-bfa-assets)), and every
date in the table above is computed from it in `lib/notice-schedule.ts`. There
is deliberately **no second due-date column**, no per-notice date, and no stored
copy of the schedule beyond the one pending job — so correcting the date
reschedules the chain instead of leaving four rows to reconcile by hand.

The intervals are platform constants, not purveyor configuration. That is a
confirmed client decision (PRD § 9, *Late-notice intervals*), and the constants
live in `lib/notice-schedule.ts` rather than in `water_purveyors` so there is no
column a future screen could expose by accident.

### "Approximately two months" means two calendar months

The requirement says *~2 months before the due date*. The implementation pins
that down as **two calendar months, clamped to the end of the target month**, in
one exported constant — `REMINDER_LEAD_MONTHS` — that nothing else duplicates:

- two months before 15 June is 15 April;
- two months before 30 April is 28 February, or 29 February in a leap year,
  because 30 February does not exist.

Calendar months rather than 60 days or eight weeks, because a purveyor checking
whether a reminder went out on time reads a calendar, and "the fifteenth, two
months earlier" is what they see there. The clamp is the only case where the day
number moves; the bare `Date` constructor would roll into March instead, putting
a reminder in the wrong month.

The same constant is used by the SQL that recomputes `asset_status`, through
`make_interval(months => …)`. Postgres clamps a whole-month subtraction from a
`date` exactly as the TypeScript does, so the two cannot disagree.

### Dates are evaluated in Pacific/Honolulu

Every business date is a Hawaii calendar day. The server runs in UTC on Vercel,
in local time on a laptop, and in whatever a Docker host is set to, and none of
those may decide which day a notice goes out on.

`lib/honolulu-dates.ts` is the only place a zone is consulted. It draws a hard
line between two kinds of value:

- a **calendar day** is a `YYYY-MM-DD` string with no zone and no time — the
  spelling a Postgres `date` column compares against — and all arithmetic on it
  (`addCalendarDays`, `addCalendarMonths`) is zone-free;
- an **instant** is a `Date`, and exactly two functions cross between the two:
  `honoluluCalendarDay` and `honoluluDayStart`.

A stage's `run_at` is midnight Honolulu on its due day, which is 10:00 UTC.
Midnight *UTC* would fire a day early on the islands. The offset is read from
the zone database through `Intl` rather than hardcoded as −10:00, so a rule
change would be picked up rather than becoming a silent off-by-one.

This is deliberately not `lib/dashboard-calendar.ts`, which names the current day
in UTC and says so. Those figures are reporting aggregates where a few hours at a
month boundary shift a count; these decide when mail reaches a customer.

## The scheduler

`packages/api/src/scheduler/` — a Node timer, a Postgres table, and nothing
else. No Vercel Cron, no OS cron, no provider queue: a hard portability
constraint, because the platform has to be deployable from a plain Dockerfile
without rewriting its background work. All durable state is in `scheduled_jobs`,
so the process is disposable.

| Module | What it owns |
|---|---|
| `config.ts` | tick interval, batch size, attempt ceiling, backoff, staleness and hold windows |
| `jobs.ts` | every statement that touches `scheduled_jobs` |
| `notice-chain.ts` | the three things the routers do to a chain: reconcile, cancel, resume |
| `notice-handler.ts` | the handler behind all four stages |
| `asset-status.ts` | recomputing `bfa_assets.asset_status` |
| `index.ts` | the tick loop, startup recovery, and the handler registry |
| `logging.ts` | the closed list of structured event names |

### A tick

1. Recompute `asset_status` from `annual_test_date` — one statement that writes
   only the rows whose status is wrong.
2. Claim up to 25 due jobs, `pending → running`, in one conditional statement.
3. Run each through its handler, applying the retry policy to anything that
   throws.

Jobs run one at a time rather than in parallel: a batch is a handful of queries
and one provider call each, and serial execution keeps the connection pool out of
failure modes that buy nothing user-visible.

### Where it is switched on

`apps/web/src/instrumentation.ts`. Next runs `register()` once per server
process before the first request, which is exactly the hook an application-level
scheduler needs; nothing in that file is Vercel-specific, so it runs the same way
under `next start` in a container.

It is gated on the `SCHEDULER_ENABLED` server variable, which **defaults to
off**. The schedule lives in the table, so a process that does not tick is not a
process with a broken schedule — it is simply not the one doing the work. That
keeps a developer's checkout and CI from mailing anybody on a timer, and leaves
switching it on a deployment decision. More than one instance ticking is safe;
the claim is atomic.

| Variable | Required | Default | Purpose |
|---|---|---|---|
| `SCHEDULER_ENABLED` | no | `false` | `true` makes this process run the tick loop. Validated in `packages/env/src/server.ts` |

Two other things have to be true before a customer receives a *reminder-chain*
notice, and neither is configuration this feature owns:
`EMAIL_DRIVER=provider` (otherwise every notice is written to a structured log
line instead of being delivered — see
[the email layer](/docs/invitations-onboarding#configuration)), and
`wp_feature_flags.automated_notices` switched on for the purveyor. The
[failure notice](#workflow-3--the-failure-notice) needs only the first: it is
not an optional add-on and checks no flag.

### Startup recovery

On boot the loop reclaims the `running` rows a previous process died holding —
found by age, using the `set_updated_at` trigger the table already has, so there
is no second lease column to keep in step. A handler does one template read and
one send, so a row still `running` after ten minutes is abandoned rather than
slow.

Overdue `pending` rows need no separate recovery path. The claim query takes
anything whose `run_at` has passed, whether that was a minute ago or during last
month's outage, which makes "process missed jobs on boot" a property of the claim
rather than a second code path that could drift from it.

### Claiming is atomic

```
update scheduled_jobs set status = 'running'
 where id in (
   select id from scheduled_jobs
    where status = 'pending' and run_at <= $now
    order by run_at, created_at
    limit $batch
    for update skip locked
 )
   and status = 'pending'
```

One statement. `FOR UPDATE SKIP LOCKED` means a second process ticking in the
same second takes a disjoint set rather than blocking on it or claiming it twice;
the outer `status = 'pending'` says the same thing again, for the day somebody
changes the locking clause.

Claiming does **not** consume an attempt. `attempts` counts failures, and a job
picked up and held because its assembly has no customer has not failed at
anything.

### One live job per stage per assembly

`0012` adds a partial unique index on (`bfa_asset_id`, `job_type`) where the
status is `pending` or `running`. Two pending reminders for one asset are not two
reminders — they are two copies of the same one, and they would both fire; two
clerks saving a date change at the same instant is enough to create them. The
index makes that unrepresentable. It is also the `ON CONFLICT` target that makes
scheduling a stage's successor an upsert, so a retried completion cannot queue it
twice.

It is partial on two counts: on the non-terminal statuses, so a completed
reminder and next cycle's pending one coexist; and on `bfa_asset_id is not null`,
so the customer-scoped `ag_renewal` job of Workflow 2 is not squeezed into an
asset-shaped rule.

### Delivery guarantee — provider idempotency keys

An email cannot join a Postgres transaction, so the database alone cannot know
whether a request the process sent just before dying was accepted. The pipeline
therefore does not try to know. It asks the provider again, in a way the
provider guarantees is safe to repeat.

**The mechanism.** Resend de-duplicates `POST /emails` requests that carry the
same `Idempotency-Key` header for 24 hours: a repeat returns the *original* email
id and sends nothing, and a repeat whose payload differs is refused with 409
`invalid_idempotent_request`. The installed SDK (`resend` 6.28.0) exposes it as
the `idempotencyKey` option on `emails.send`, which sets that header.
`providerDriver` passes it through; nothing in the notice handler calls Resend.

**How the handler uses it** (`0013_scheduled_job_delivery_outcome`):

1. **One key per job.** `bfa-notice/<scheduled_jobs.id>`. A job row is one stage
   of one assembly's chain in one cycle, so its key names exactly one email. A
   date change creates a new row, and therefore a new key.
2. **Freeze the whole request, then send.** Everything Resend sees in the
   request body is written to `delivery_payload` once, with
   `delivery_attempted_at`, before the first provider call:

   | Body field | Source at the first attempt |
   |---|---|
   | `to`, `subject`, `html`, `tags` | rendered from the template and the asset's current customer |
   | `from`, `replyTo` | the provider's configured sender (`RESEND_FROM_EMAIL`, `RESEND_REPLY_TO`), read once through `resolveSenderIdentity` |

   Every retry sends exactly that stored body. Nothing is re-rendered and
   nothing is re-read from the environment: a template edited, a customer
   reassigned, **or the sender variables rotated** between attempts would each
   change the body, and the provider would refuse the key with 409 instead of
   returning the original id. The sender travels to the driver as
   `EmailMessage.sender`; `providerDriver` uses it in place of the environment
   only when it is present, so ordinary mail — invitations, broadcasts — still
   sends as the current configuration.

   Every payload this version freezes has a `sender` key, in one of two forms:
   `{ from, replyTo }` for the provider driver, or an explicit `null` for a
   driver with no sender to pin (the console driver), which is safe to replay.
   A payload with **no `sender` key at all** is something else — see
   [legacy payloads](#legacy-payloads-without-a-frozen-sender). The handler tells
   the three apart by whether the key is present, never by treating absent as
   `null`.
3. **Record only what the provider confirmed.** `provider_message_id` and
   `delivered_at` are written after the provider answers with an id, and only
   then. The frozen payload is cleared in the same statement.
4. **Advance only after the record is durable.** The next stage is scheduled in
   the completion transaction, which runs after the delivery record has
   committed.

**What that gives, crash by crash:**

| The process dies… | On restart | Result |
|---|---|---|
| before the payload is frozen | nothing was attempted; the job is retried from the start | one email |
| after freezing, before the request leaves | the retry sends the frozen body with the job's key; the provider has never seen it | one email |
| after the provider accepted, before its answer was recorded | the retry sends the identical body — sender included — with the same key; the provider returns the original id and sends nothing | **one email** |
| after the answer was recorded, before completion | `provider_message_id` is on the row; the retry sends nothing and completes | one email, one successor |

A **refusal** — the provider throws, or returns no id — records nothing, keeps the
payload frozen, and puts the job back on the retry schedule with no successor.
The next attempt uses the same key.

**The one bound, stated.** The provider's window is 24 hours. A retry after that
could not be de-duplicated, and the outcome of the first attempt could no longer
be learned. The handler does not guess either way: if a job's first attempt is
more than 23 hours old (an hour's margin for clock skew) and no outcome is
recorded, the job is marked `failed` with *"delivery outcome unknown"*, a
`scheduler_delivery_unconfirmed` line is logged with the idempotency key, and no
next stage is scheduled. Ordinary retries finish in about a quarter of an hour;
this is reached only if the process is down for most of a day between an attempt
and its retry. It is a visible row for a person to check against the provider's
log, not a silent loss and not a silent duplicate.

#### Legacy payloads without a frozen sender

A job frozen by the earlier version of this handler stored the content but not
the sender: its `delivery_payload` has no `sender` key. The `from` and `replyTo`
of its first provider request were read from `RESEND_FROM_EMAIL` and
`RESEND_REPLY_TO` at the time and never recorded, so that request body **cannot
be rebuilt**. If the provider accepted it and the answer was lost, a replay
would either carry the current sender — a different body under the same key,
refused with 409 if the variables have changed — or a guess. Neither is a safe
retry, and this does not depend on age: such a row is unsafe to replay a minute
after its attempt, not only after 24 hours.

So when the handler finds an unsettled legacy payload (no `provider_message_id`,
no `sender` key), it:

- makes **no provider call**;
- marks the `running` job `failed` with *"delivery outcome unknown"* and a
  reason naming the missing sender identity;
- logs `scheduler_delivery_unconfirmed` with the job id, the idempotency key and
  `cause: "legacy_sender_not_frozen"`;
- schedules **no next stage** — the same rule as any unconfirmed delivery.

A person can check the provider's log for that idempotency key and resend if
nothing went out. Legacy rows already settled (`provider_message_id` recorded)
are unaffected: they have nothing left to send.

**After an attempt, recipient and sender are fixed.** Once a payload is frozen,
the attempt is settled by replaying it to the customer it was rendered for, from
the sender it was first sent as. A reassignment or a sender change made in
between takes effect from the next stage — a new job, a new key, a new body. The asset, the
feature flag and cancellation are still checked on every pass, so a passing test
or a switched-off flag still stops a retry.

**The console driver** honours the key the same way within its own process, so
local development and the test suite exercise the same retry path without a
provider account.

### Retries

A delivery that throws increments `attempts`, records the provider's message in
`last_error`, and re-queues the job with an exponential backoff — a minute,
doubling, capped at an hour. At five failures the job is `failed` and terminal.

A failed stage **schedules nothing**. The chain stops there, visibly, rather than
escalating to a customer who never received the notice before it. That follows
the plan's rule that each *successful* notice schedules its successor, and it is
the behaviour a purveyor can act on, because a `failed` row with a `last_error` is
something they can see and ask about. See
[remaining product decisions](#remaining-product-decisions).

### The chain is never pre-created

Each successful notice schedules exactly one successor. A pending `final_notice`
sitting in the table for two months would be a notice that a passing test, a
corrected date and a switched-off feature flag all have to remember to cancel —
and a row that does not exist yet cannot be forgotten.

It also means "the chain" is at most one live row: the stage that has not
happened. Cancelling, rescheduling and resuming all deal with that one row.

## What the handler checks, in order

`notice-handler.ts` is one function for all four stages, not four. They differ in
exactly three ways — which template row is used, whether the certifier list is
appended, and which stage comes next — and all three are lookups. Four handlers
would be four copies of the tenancy, flag, recipient and rendering rules, and the
failure mode of that is a late notice that checks something the reminder does
not.

Nothing is read from the job row except which asset and which stage. Everything
else is resolved **at send time**.

### 1. The asset, scoped to the job's purveyor

`scheduled_jobs` carries a `water_purveyor_id` and so does the asset; if they
ever disagree — a restore, a corrected row — the job is not that purveyor's to
run. A job whose asset is gone, has moved tenant, or has lost its annual test
date is `cancelled`, not `failed`.

### 2. The feature flag, read now

Automated notices are an optional paid add-on the Super-Admin switches on per
purveyor through `wp_feature_flags.automated_notices` (PRD § 9). **A missing row
is off** — the default state of every new tenant, and never permission to start
mailing their customers.

The flag is checked when the job **runs**, not only when it is scheduled.
Switching the feature off has to stop notices that are already queued, not merely
prevent new ones. A job that finds the flag off is marked `cancelled` with the
reason in `last_error` — deliberately not `failed`, because switching off a paid
add-on is not a delivery problem and must not be retried as one.

Scheduling therefore does not consult the flag at all. That costs one row that
will cancel itself for a purveyor without the add-on, and buys the property that
switching the flag *on* needs no backfill.

### 3. The recipient, through the asset's current customer

Resolved from `bfa_assets.current_customer_id` at send time, scoped to the
asset's own purveyor as well as by id. A job queued two months ago must not carry
a customer id: by the time it runs the occupant may have changed, and mailing a
former occupant a notice about somebody else's assembly is the exact mistake the
asset-centric data model exists to prevent (PRD § 5).

The purveyor scope on the customer lookup is load-bearing even though
`assignCustomer` refuses to point an asset at another tenant's customer. A row
written before that rule, or restored from a backup, is not bound by it — and a
notice is the one place a mispointed row would be mailed to the wrong company's
customer.

### 4. The text

The purveyor's `notice_templates` row for this stage where they wrote one, the
platform default where they did not — column by column, because `subject` and
`body` are both nullable and half a template saved is not a reason to send half an
email. That is the same rule `listNoticeTemplates` applies when it renders the
editor, so what a purveyor previews is what a customer receives. See
[WP Notices & Email](/docs/wp-notices#a-missing-row-is-a-meaning-not-an-absence).

`notice_templates.is_enabled` is **not** read. Whether a purveyor sends automated
notices at all is the feature flag; a per-stage switch is a control with
undefined behaviour until what disabling a middle step means for the escalation
chain is answered, and reading the column here would be building it by accident.

The six registered variables — `{{customer_name}}`, `{{wp_name}}`,
`{{bfa_type}}`, `{{bin}}`, `{{service_address}}`, `{{due_date}}` — are
substituted by the same `renderTemplate` the browser previews with. The variable
set is unchanged by this workflow; see
[Dynamic values](/docs/wp-notices#dynamic-values).

### 5. The send

One path, shared with every other email in the application:

```
renderTemplate → renderTextEmail → sendEmail
```

`renderTextEmail` runs the text through `templateToHtml`, which escapes all of it
and turns only line breaks into paragraphs, then wraps it in the one shared
layout from `lib/email-layout.ts`. There is no HTML notice template and no
rich-text editor: a customer name containing a tag is text, not an element.
Nothing here talks to Resend — `sendEmail` selects the driver and emits one
structured line per attempt, so the whole workflow is testable with no provider
account.

### 6. The successor

Completed and scheduled in one transaction, and only while this job is still
`running`. Between a handler starting and finishing, a passing test or a
corrected date may have cancelled the row; an unconditional completion would put
`completed` back over `cancelled` and then schedule the successor it was
cancelled to prevent.

## The certifier list on the reminder

The reminder is the one notice that has to be actionable: it says a test is due,
so it has to say who can do it. The list is every tester who is **both**

- authorized for this purveyor with `authorization_status = 'active'`, and
- active on the platform with `certifiers.status = 'active'`.

Those two columns mean different things and both are load-bearing. An
authorization revoked by this purveyor still leaves the tester working for others;
a blocked certifier works for nobody. Either one is a name that must not appear in
this email. The pair is also why
[WP Certifiers](/docs/wp-certifiers)' open question about global-versus-per-WP
blocking matters: this workflow already reads the two as separate facts.

Resolved at send time, never cached and never stored on the job — a certifier
blocked yesterday must not appear in today's reminder.

The block is **appended below** the purveyor's text rather than being a seventh
template variable. `NOTICE_VARIABLES` is a closed registry whose final contents
are still a client decision, and a list that depended on the purveyor having typed
a placeholder would be missing from every template that predates it. Each line is
name — company — licence number, skipping whatever is absent; `certifiers` has no
phone or email column, so no contact field is invented.

When nobody qualifies the block is omitted entirely rather than rendered as an
empty heading, and the notice still goes out. The notice is the obligation, the
list is help, and a purveyor with no active authorized tester has a problem the
customer cannot solve. The count is on the `scheduler_job_completed` log line.

Late notices do not carry the list. A late notice is a compliance escalation
rather than an offer of help, and the customer had the list two months earlier.

## Hold and resume

A suspended customer holds the asset's **whole notice pipeline** until the
purveyor attaches a new customer to the BIN. That is a confirmed decision
(PRD § 9, *Email routing / suspended customers*) and it is not a per-email skip.

The handler holds — sends nothing, advances nothing — when the asset has no
current customer, when that customer is suspended, or when they have no email
address. The job stays `pending`, keeps its full retry budget (a hold is not a
failure), is re-queued a day out, and carries the reason in `last_error` for
whoever asks why no notice arrived.

### The resume point, stated

The plan says the pipeline holds until a new customer is attached but does not
define where it picks up. What ships is the smallest durable reading:

> **When `assignCustomer` attaches an *active* customer, the single unsent stage
> resumes, and nothing already sent is replayed.**

Because the chain is never pre-created, the only live row is the stage that has
not happened. If its due day has already passed in Hawaii it is pulled forward to
run on the next tick; if it is still in the future it is left alone — resuming
undoes a wait, it does not send a notice early. A stage that already sent is a
`completed` row that the resume cannot reach.

So a customer attached three months into an escalation receives the stage that
was waiting — not the reminder and two late notices the previous occupant's
suspension swallowed.

Attaching a **suspended** customer continues the hold, which is the rule itself.
The hold interval is a one-day ceiling on how late a resumed notice can be if
that reconciliation is ever missed, not the normal path — the normal path is the
`assignCustomer` write.

Two other readings are real and were not chosen, both because they are product
decisions rather than engineering ones:

- **restart from the reminder** — mails a new occupant about a deadline that has
  already passed;
- **skip to whichever stage the calendar now says is due** — can take a customer
  from silence straight to a final notice.

Either is a change to `resumeHeldNoticeChain` and its tests. Flagged in
[remaining product decisions](#remaining-product-decisions).

## What the routers do

Five mutations touch a chain, and each one does it **inside its own
transaction** — a reminder scheduled for an asset whose insert then rolled back
would be a job with no assembly behind it, mailing a customer about a valve that
was never registered.

| Mutation | What happens |
|---|---|
| `assets.createAsset` | schedules the reminder for the new asset's annual test date |
| `assets.updateAsset` | on a **changed** `annual_test_date`: cancels every live stage — the reminder included, `pending` or `running` — and inserts one fresh reminder for the new date |
| `assets.assignCustomer` | on an **active** customer: resumes the waiting stage |
| `submittedTests.updateSubmittedTest` | on a submitted passing test: cancels every remaining stage |
| `submittedTests.linkSubmissionAsset` | on a submitted passing test: cancels every remaining stage |

### Correcting the date reschedules the chain

Every stage hangs off one date, so any live job computed from the old one is a
notice about a deadline that no longer exists. On a date change **every** live
stage is cancelled with the reason recorded — the reminder included, whether it
is `pending` or already `running` — and exactly one fresh reminder is inserted for
the new date.

The `running` case is the one that matters. A reminder the loop has already
claimed may be mid-send; a running row is deliberately never rewritten, so the
only way to stop it is to cancel it. Its handler then finds the row taken: if it
had not sent yet it sends nothing, and if the email was already in flight the
provider's answer is still recorded as the fact it is — but the completion is
refused and **no late notice is scheduled from the old date**.

The replacement is a new row with a new id, and therefore a new provider
idempotency key, so it can never be mistaken for an attempt made against the old
date.

A date change and a handler finishing a stage serialise on the asset's row lock
(`lockAssetForChain`), as does a passing test. Without it a date change could
commit while a handler's successor insert was still invisible to it, and that
successor would survive, computed from the old date.

The reminder is scheduled **even when its day is already in the past**. That is
what makes a purveyor who registers a long-overdue assembly get the escalation
rather than silence: the stage fires on the next tick, its successor is scheduled
immediately after, and the chain catches up in order. It is also the build plan's
acceptance criterion — *the full escalation fires in order against a seeded
past-due asset*.

### Nothing is written when nothing changed

Reconciliation is guarded twice. The mutations only reconcile when
`annual_test_date` actually moved, so correcting a service address does not touch
the schedule; and the reconciler itself returns without writing when the chain is
already exactly one live reminder at the target `run_at`, so a redundant
reconciliation cancels nothing, inserts nothing, moves no `updated_at` and emits
no scheduling line. The same rule the asset and template mutations follow for a
save that changes nothing.

### A passing test ends the chain

Every query in the submitted-tests router pins `status = 'submitted'`, so a draft
is not merely unlisted — it names no row at all. That is the rule, not a side
effect: a half-finished test is the certifier's working copy and has not been
attested to, so it cannot stop a purveyor's escalation. A **failed** test cancels
nothing either; the assembly is still untested as far as compliance is concerned,
and Workflow 3 is what responds to a failure.

Cancellation reaches `running` rows as well as `pending` ones, and the handler's
completion refuses a row that has been taken. That closes the race where a
passing test arrives while the reminder is mid-send: the cancellation wins, and no
late notice is queued behind it.

The certifier wizard (PRD § 6.5) does not exist yet, so the only paths that turn a
submission into a passing test today are the two WP corrections above. Both now
route through one exported lifecycle helper — see the next section — which the
wizard's submit path calls when it lands.

## One lifecycle helper for a submitted result

`applySubmittedTestResult` (`scheduler/submission-lifecycle.ts`) states, once,
what a submitted test's `(bfa_asset_id, test_result)` pair means for the notice
machinery. `updateSubmittedTest` and `linkSubmissionAsset` both call it inside
their own transaction, and the certifier wizard's submit calls the same
function when it lands — no caller re-derives which chains to cancel and which
notices to queue:

| The row is now | What happens |
|---|---|
| a **linked pass** | the assembly's escalation chain is cancelled, and this submission's own *unsent* failure notice is withdrawn (a correction just un-failed it) |
| a **linked fail** | this submission's one failure notice is queued, due immediately. Nothing is cancelled — the assembly is still untested as far as the escalation is concerned |
| **neither** (result cleared, or still unlinked) | its unsent failure notice, if any, is withdrawn; no chain is touched |

Drafts never reach it: the submitted-tests router pins `status = 'submitted'`
on every query, and the wizard calls it only at submit — so a failed draft
sends nothing and appears nowhere, by construction.

## Workflow 3 — the failure notice

Not a chain: one email per submitted failing test, sent to the assembly's
current customer, listing the purveyor's active repair companies. **Not
gated** — the client named automated reminders and the AG renewal as the
optional paid features, not the failure notice, so no `wp_feature_flags` check
runs anywhere in this path. If that turns out to be wrong it is one flag check
at the top of the handler.

**The email is immediate; the fail list is not.** The notice is queued the
moment a failed test is submitted. The assembly reaches the WP's
[fail list](/docs/wp-dashboard#the-fail-list) only once that failure has gone
30 days without a passing re-test (PRD § 6.8) — a rule applied when the list
is read, not by anything this path writes or schedules. A passing re-test is a
new submitted record; when it arrives, the earlier fail's still-unsent notice
is cancelled by the handler's later-pass check below rather than by the
lifecycle helper.

### Delivered through the scheduler, not inline

The mutation that records a linked fail does not send mail. It queues one
`failure_notice` job — due immediately, in the same transaction as the write
that justifies it — and the next tick (at most a minute later) delivers it. An
email is an external side effect the transaction cannot take back, and the
scheduler already owns everything that makes a send survive crashes without
duplicating: the frozen payload, the provider idempotency key, retry with
backoff, startup recovery. A rolled-back correction leaves no job behind.

That machinery is now literally shared: the freeze/replay/record sequence was
extracted from the notice handler into `scheduler/delivery.ts`
(`settleJobDelivery`), and both handlers run their delivery through it. The
[delivery guarantee](#delivery-guarantee--provider-idempotency-keys) above —
one email per job, outcome recorded only from the provider's answer, *delivery
outcome unknown* rather than a guess past the idempotency window — applies to
the failure notice verbatim.

### The job carries the submission, not the asset

`scheduled_jobs.test_submission_id` (migration `0014`) names the submitted
failing test the job answers; `bfa_asset_id` is deliberately null on these
rows. The live-asset uniqueness rule allows one live job per (asset, type), and
two failing submissions for one assembly in quick succession are **two failure
notices** — each submitted fail triggers its own — so the job is keyed by what
it actually answers.

Its own uniqueness rule is stricter in the other direction: a partial unique
index over `(test_submission_id, job_type)` covering every status **except
`cancelled`** makes "at most one non-cancelled failure notice per submission" a
database fact. Scheduling is an upsert-do-nothing against it, so a still-failing
row saved again, a retried mutation, or two clerks at once cannot queue a second
email about a fail the customer was already told about — even after the first
one was delivered. Only a cancellation (the fail was corrected away) frees the
slot, so correcting a result to pass and back to fail earns exactly one fresh
notice.

### What the failure handler checks, in order

Everything is re-decided from current state on every pass, including a retry:

1. **The submission**, scoped to the job's purveyor. Gone, no longer submitted,
   no longer a fail, or never linked — `cancelled`, not failed.
2. **The assembly**, through the submission's own link and tenant-checked
   against the submission's purveyor. A link that crossed tenants is never
   mailed.
3. **The relevance check**: a submitted *pass* filed after this fail — in
   submission-event order, `(created_at, id)`, never the certifier-typed
   `test_date` — cancels the notice instead of sending it. The same comparison
   the [fail list](/docs/wp-dashboard#the-fail-list) makes, so a customer whose
   assembly has since passed is not told to arrange repairs.
4. **The recipient** — the asset's *current* customer, resolved through exactly
   the same exported rules as the reminder chain (`resolveRecipient`): tenant
   scoped, and a missing, suspended or email-less customer **holds** the job
   (pending again, a day later, no attempt consumed) rather than failing it.
5. **The delivery**, through the shared settlement above.
6. **Completion**, with no successor.

### What the email contains

Fixed copy in `lib/failure-notice-copy.ts` — provisional wording in the same
register as the notice defaults, flagged for client approval. There is
deliberately **no `notice_templates` row and no editor** for it: the
`notice_type` enum names the four escalation stages only, and a configurable
failure template is not a specified feature.

The repair-company block is resolved **at send time** — the purveyor's
`repair_companies` rows with `status = 'active'`, never cached and never stored
on the submission, so a company deactivated yesterday is not in today's email.
Each entry is **name and phone only**: the entry type has no email field at
all, so a repair company's address cannot reach a customer's inbox without two
files changing on purpose. With nobody active to list, the block is omitted
rather than rendered empty, and the notice still goes out.

Everything renders through `renderTextEmail` — the one escaped path every
automated message takes — so markup in a customer or company name is inert.

## `asset_status` is scheduler-owned

`bfa_assets.asset_status` is recomputed from `annual_test_date` on every tick and
is written by nothing else. No mutation accepts one, the asset form shows it
read-only, and `0004`'s column grants never handed the privilege over. That is why
the dashboard can say "the assets the scheduler has marked past due" and mean it.

| Value | Rule |
|---|---|
| `past_due` | the due date has passed |
| `due_soon` | from the reminder day up to **and including** the due date |
| `active` | otherwise, including an asset with no annual test date |

The due date itself is `due_soon`, not `past_due`: that is the last day the test
can still be done, and it is why late notice 1 is due the day after. The
`due_soon` window opens on the reminder day, so a purveyor seeing `due_soon` on a
row can assume the customer has been written to.

One statement for the whole table, with `where asset_status <> <computed>`, so an
ordinary day writes nothing, moves no `updated_at` and emits no log line. "Today"
is computed in Hawaii and passed in as a `date` — letting Postgres use
`current_date` would name the day in the server's zone, and for the last fourteen
hours of every Hawaii day an assembly due today would already read `past_due`.

## Logging

Every scheduler action emits one structured JSON line, in the same shape the
feature routers use (`actor_id`, `effective_profile_id`, `wp_id`, `asset_id`,
`timestamp`). The scheduler's writes are the ones with no human behind them,
which makes the log the only account of what happened.

`actor_id` is null on a line the loop produced by itself, and carries the acting
profile on a line a purveyor's own save caused — scheduling a reminder after an
asset's date is corrected is that person's action as much as the row they edited.

The event names are a closed list in `scheduler/logging.ts`:

| Event | Meaning |
|---|---|
| `scheduler_job_scheduled` | a new asset's reminder, or a date change's replacement reminder |
| `scheduler_delivery_recorded` | the provider confirmed the email — job id, idempotency key, provider message id, `delivery_pass`; no address or body |
| `scheduler_delivery_unconfirmed` | the first attempt cannot be safely replayed — past the provider's idempotency window (`cause: "idempotency_window_expired"`), or a legacy payload with no frozen sender (`cause: "legacy_sender_not_frozen"`); failed for a person to check. Terminal |
| `scheduler_job_cancelled` | withdrawn: passing test, changed date, flag off, gone asset |
| `scheduler_job_resumed` | a held, already-due stage pulled forward |
| `scheduler_job_claimed` | the loop took ownership |
| `scheduler_job_completed` | the stage did what it exists to do |
| `scheduler_job_held` | nothing sent, chain not advanced |
| `scheduler_job_retrying` | a delivery failed; it will be tried again |
| `scheduler_job_failed` | the attempt ceiling was reached. Terminal |
| `scheduler_job_recovered` | a `running` row left by a crash was reclaimed |
| `scheduler_job_superseded` | the job was cancelled under a running handler |
| `scheduler_tick` | one pass of the loop, and what it did |
| `scheduler_started` / `scheduler_stopped` | the loop's own lifecycle |
| `scheduler_asset_status_recomputed` | statuses changed, and how many |

Idle ticks log nothing. A line a minute, forever, saying nothing happened would
bury the lines that matter.

## Row policies

`0012_scheduled_job_policies` gives `scheduled_jobs` its first policies. RLS was
enabled on the table in `0000`; until now it had no policies, so nothing reaching
it through PostgREST could see a row.

**Read-only for everybody, with no exception for the Super-Admin.** There is no
INSERT, UPDATE or DELETE grant at all — not a narrow one, none. Every write goes
through the service-role scheduler process, which bypasses RLS, so a job row is a
record of what the platform did or is about to do, and a user editing one would be
editing the audit trail of their own mail.

| Actor | Access |
|---|---|
| Super-Admin | `SELECT` across every tenant |
| `wp_admin`, `wp_sub_admin`, `wp_employee` | `SELECT` their own purveyor's rows |
| Certifier | nothing |

The WP read is genuinely useful: "no reminder arrived" is answered by looking at
whether a job exists, whether it is `cancelled` because the feature flag is off, or
`failed` with a `last_error`. Caller resolution goes through the two SECURITY
DEFINER helpers from `0001`, so a blocked profile resolves to NULL here as
everywhere else and keeps no access.

The application reads and writes through the privileged Drizzle connection, which
bypasses all of this — the two boundaries are independent and neither substitutes
for the other. `packages/db/src/scheduled-jobs-rls.test.ts` covers the second.

## Remaining product decisions

- **Where a held pipeline resumes.** Shipped as "the single unsent stage
  resumes, nothing already sent is replayed" — see
  [the resume point](#the-resume-point-stated). The two alternatives are
  restarting from the reminder and skipping to whichever stage is now due.
- **Whether a terminally failed stage should stop the chain.** It does today: a
  stage that exhausts five attempts schedules nothing, so a long provider outage
  at the reminder means no late notices for that cycle. The alternative — advance
  the chain anyway so the escalation is not lost — is one branch in
  `recordJobFailure`'s caller, and it trades a visible `failed` row for a
  customer who is escalated past a notice they never received. The same rule
  applies to a *delivery outcome unknown* failure past the provider's window.
- **Customer-facing copy for the four platform defaults.** Still provisional in
  `lib/notice-defaults.ts`, and still blocking a production release of this
  workflow. It now includes the certifier-block heading.
- **The full dynamic-variable list.** Six variables ship, unchanged by this
  workflow. A seventh is an entry in `NOTICE_VARIABLES` plus a value in the
  handler's `values` object (PRD § 10).
- **Whether a blocked water purveyor should send automated mail.** The gate today
  is the feature flag alone; `water_purveyors.status` is not consulted, because
  no requirement asks for it and what blocking a purveyor means for their
  customers' compliance deadlines has not been decided.
- **The failure notice's customer-facing copy.** Provisional in
  `lib/failure-notice-copy.ts`, same register and same caveat as the notice
  defaults: plain statements, no compliance claim, awaiting client wording.
- **The failure-episode rule.** An episode starts at the first submitted fail
  after the last submitted pass, and later fails inside it do not reset the
  fail list's 30-day clock or its age — a stated project default
  ([details](/docs/wp-dashboard#membership-is-computed-never-stored)), chosen
  because no existing test or requirement pinned it down. Changing it is one
  SQL expression and its tests.
