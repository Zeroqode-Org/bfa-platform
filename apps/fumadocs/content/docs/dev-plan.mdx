**App Shell (6.15)**: the workspace picker on `/` is gone. It was a development
shortcut from before roles were resolved server-side; `/` now forwards each
signed-in user to their own dashboard by role, and anonymous visitors to
`/login`. See [Where people land](/docs/invitations-onboarding#where-people-land).

**WP Dashboard — Core & Analytics (6.6.1)**: shipped. `/wp` is no longer a
placeholder. Five WP-scoped read procedures in a new `dashboard` router back the
five build-plan metric cards, an incoming-reports list, a delinquent-asset list,
a trailing-twelve-month compliance trend and a pass/fail breakdown over a
selectable range. **No migration ships with it** — it reads what the assets and
submitted-tests features already store, through indexes those features already
put there.

Two decisions worth carrying forward. The build plan's *"submissions awaiting
review"* card ships as **Submitted reports**, counting `status = 'submitted'`:
the schema has no review lifecycle, and rather than invent one the card was
renamed to what it actually counts, with a line on the card saying it is an
incoming total and not a queue that drains. And the screen shows the build
plan's **five** cards rather than the approved prototype's six — Certifiers and
Customers are prototype-only, and both already have a screen of their own in the
sidebar.

The pass/fail breakdown returns `pass`, `fail` and `total` and nothing else;
submitted rows with no recorded result are reported as
`supplemental.unrecorded` and shown as a note beneath the chart rather than as
part of it. All date filtering is calendar-date comparison against Postgres
`date` columns — the one zone-dependent step is naming the day "now" falls on,
done in UTC.

Incoming reports do not get a detail view of their own. A row links to
`/wp/tests?test=<id>`, and the existing Submitted Tests screen opens that record
in its own document dialog — so the document, the corrections form, the
link-to-asset flow and the role check stay in one place. The two share the
ordering constant as well, so the dashboard's rows really are the head of that
list. Full writeup: [WP Dashboard — Core & Analytics](/docs/wp-dashboard).

**WP Dashboard — Customers (6.6.4)**: shipped. `/wp/customers` creates, edits
and suspends customers through three WP-scoped procedures, `customers` has row
policies for the first time, and suspension states plainly that it pauses
automated email for the customer's currently assigned assets. Workflow 1 now
honours that hold: a suspended customer stops the asset's notices without
advancing the chain. Full writeup: [WP Customers](/docs/wp-customers).

**WP Dashboard — BFA Assets (6.6.2)**: shipped. `/wp/assets` registers, lists
and corrects assets through five WP-scoped procedures, and `bfa_assets` and
`customer_assignments` have row policies for the first time. A BIN can be
corrected and every change is logged with both values; attaching a customer
closes the outgoing occupancy row and opens a new one in one transaction, so the
asset detail view can show the whole history rather than only the current
occupant. The annual test date entered here is what Workflow 1 schedules
against, and `asset_status` — read-only on the screen — is now recomputed from
it on every scheduler tick. Full writeup:
[WP BFA Assets](/docs/wp-bfa-assets).

**WP Dashboard — Repair Companies (6.6.5)**: shipped. `/wp/repair-companies`
creates, edits and deactivates approved repair firms through three WP-scoped
procedures, and `repair_companies` has row policies for the first time.
Deactivation flips `status` to `inactive` and nothing else — there is no delete
procedure, no delete control and no DELETE grant, so a company that stops being
recommended keeps the record a past failure notice was built from. Workflow 3
now reads `status = 'active'` at send time, exactly as planned.
Full writeup: [WP Repair Companies](/docs/wp-repair-companies).

**WP Dashboard — Certifiers (6.6.3)**: shipped. `/wp/certifiers` lists the field
testers authorized for the purveyor, invites new ones, and blocks or unblocks
them through two WP-scoped procedures. `certifiers` has row policies for the
first time, and they are the first join-based ones in the schema — a certifier is
not a tenant of a purveyor, so the reach runs through
`wp_certifier_authorizations` rather than through a `water_purveyor_id` column.
The purveyor owns exactly one column of the record: `status`.

Two migrations, not one. `0007` corrects a defect in `0006`, which capped column
writes with `GRANT UPDATE (status) TO authenticated` — a grant belongs to the
Postgres role, and PostgREST gives every signed-in user the same one, so the cap
meant for water purveyors also hit the Super-Admin and the certifier. The
per-actor narrowing now lives in a `BEFORE UPDATE` trigger, which is the only
object able to see the old row and the new one; WP effective access is unchanged
and asserted directly.

Blocking now genuinely denies access rather than labelling a row.
`certifiers.status` is read by `resolveCaller` next to `profiles.status`, and
folded into `private.current_global_role()` / `private.current_wp_id()`, so a
blocked certifier loses every role-scoped policy in the schema and not only this
table. The invite dialog reuses `invitations.createInvitation` — no second
invitation backend — and the second-purveyor redemption path is unchanged. What
is deliberately not here: the certifier profile *screen* (the database now
permits the writes; § 6.3 builds the UI) and authorization revocation, which
needs policies on `wp_certifier_authorizations`.

**Carries a new open question.** Blocking writes the global `certifiers.status`,
so one purveyor can remove a multi-WP certifier's access everywhere. That is
what the build plan's acceptance criterion specifies and what shipped; it is not
in the client Q&A log, and the narrower per-WP alternative
(`authorization_status = 'revoked'`) already exists in the schema. Flagged in the
PRD rather than decided quietly. Full writeup:
[WP Certifiers](/docs/wp-certifiers).

**WP Dashboard — Submitted Tests (6.6.6)**: shipped ahead of its week, against
the seeded submissions — the wizard that produces real ones is 6.5. `/wp/tests`
lists every test filed against the purveyor across certifiers, opens one as a
document with every field editable in place, flags whatever the certifier typed
over a prefilled value, and links a submission that never found its assembly to
one of the purveyor's own assets. `0008_test_submission_policies` gives
`test_submissions` its first row policies; drafts are invisible to a WP by
predicate on every read and write path, not by filtering.

**Carries a decided answer to a standing open question, scoped to one screen.**
All three WP roles read submitted tests; only Admin and SubAdmin correct one.
PRD § 10 leaves the SubAdmin/Employee split open in general and this does not
close it — the check is local to the submitted-tests router, as 6.6.3's is to
the certifiers router. Full writeup:
[WP Submitted Tests](/docs/wp-submitted-tests).

**WP Dashboard — Notices & Email (6.6.7)**: shipped. `/wp/notices` edits the
subject and message for all four automated notice types, composes and sends a
one-off general-info broadcast to a filtered set of customers, and shows the
approved repair companies read-only. `0010_notice_template_policies` gives
`notice_templates` its first row policies. `listNoticeTemplates` always returns
four entries and fills a missing row with the platform default, so an untouched
type never sends blank and the screen has no "not set" branch. The four stored
templates are now sent by Workflow 1, which applies the same per-column fallback
so what a purveyor previews is what a customer receives.

**Carries two product decisions and one open question.** The broadcast ships
*with* personalisation, limited to `{{customer_name}}` and `{{wp_name}}`,
because a customer may own several assemblies and the four asset-scoped
variables have no single value for a recipient; and suspended customers are
excluded from every audience, following the confirmed § 9 rule that suspension
holds a customer's whole notice pipeline. Still open, and blocking a production
release of this section: the client has not supplied customer-facing text for
the four platform defaults, so `notice-defaults.ts` carries plain provisional
copy that makes no compliance claim. Full writeup:
[WP Notices & Email](/docs/wp-notices).

**Node-native scheduler + Workflow 1: Reminder and Late Notices (6.7)**: shipped
together, because neither is testable without the other. `packages/api/src/scheduler/`
is a Node timer over `scheduled_jobs` — no Vercel Cron, no OS cron, no provider
queue — switched on by `apps/web/src/instrumentation.ts` behind the new
`SCHEDULER_ENABLED` variable, which defaults to **off** so a checkout and CI never
mail anybody on a timer. `0012_scheduled_job_policies` adds a partial unique
index that makes "one live job per stage per assembly" a database fact, and the
table's first row policies: read-only for every role, with **no write grant at
all**, Super-Admin included.

**Two defects fixed after the first cut.** *(1)* A date change left a `running`
reminder live, so it could send on the old schedule; reconciliation now cancels
every live stage — reminder included — under the asset's row lock and inserts one
fresh reminder. *(2)* `0012`'s `sent_at` was written *before* the send, so a crash
in between silently lost a notice. `0013_scheduled_job_delivery_outcome` drops it:
each job now sends under a stable Resend idempotency key, replays a payload frozen
before the first attempt, records delivery only from the provider's answer, and
schedules the next stage only after that record commits. The one bound is the
provider's 24-hour key window, past which a job fails explicitly as *delivery
outcome unknown* instead of guessing.

The four stages are computed from `bfa_assets.annual_test_date` alone — reminder
two calendar months before, then +1, +32 and +63 days — and evaluated in
**Pacific/Honolulu**, so a stage's `run_at` is 10:00 UTC rather than midnight UTC,
which would fire a day early on the islands. `lib/honolulu-dates.ts` is the one
place a zone is consulted. Each *successful* notice schedules exactly one
successor, so the chain is never pre-created and at most one live job exists per
assembly. `asset_status` is now genuinely recomputed on every tick and is
scheduler-owned: the asset screen's read-only status column finally means
something.

Three things are resolved at send time and nothing is trusted from queue time:
the recipient (the asset's *current* customer, scoped to the asset's own
purveyor), the `automated_notices` feature flag, and the reminder's list of
authorized active certifiers. A job that finds the flag off is `cancelled`, not
`failed` — switching off a paid add-on is not a delivery problem. A missing or
suspended customer holds the stage without advancing the chain, and a submitted
passing test cancels every remaining stage, including one a handler is mid-send
on. Delivery goes through the existing `renderTemplate → renderTextEmail →
sendEmail` path; nothing here touches Resend and no HTML notice template exists.
The six registered variables are unchanged.

**Carries three product decisions, all stated rather than assumed.** *(1)* "~2
months" is implemented as two calendar months clamped to the end of the target
month, in one constant the `asset_status` SQL shares. *(2)* A held pipeline
resumes at **the single unsent stage, replaying nothing already sent**, when
`assignCustomer` attaches an active customer — the plan did not define the resume
point, and the alternatives (restart from the reminder; skip to whichever stage is
now due) are named in the docs. *(3)* A stage that exhausts its five delivery
attempts stops the chain rather than escalating past a notice the customer never
received. Still blocking a production release: the client's own copy for the four
notices. Full writeup: [Notice Workflow & Scheduler](/docs/notice-workflow).

**Workflow 3: Failure Notice + Fail List (6.8)**: shipped. A submitted test
that becomes a **linked fail** — by a WP correction, by the late link of a
no-BIN failure, or later by the wizard's own submit, all through one exported
lifecycle helper — queues its failure notice in the same transaction, due
immediately, and the scheduler delivers it under the same frozen-payload
idempotency guarantee as Workflow 1 (`0016` adds `failure_notice` to `job_type`
and `test_submission_id` to `scheduled_jobs`; the delivery sequence itself was
extracted to `scheduler/delivery.ts` and shared). The email lists the
purveyor's **active** repair companies, resolved at send time, name and phone
only — never a repair company's email — and a pass submitted after the fail
cancels the unsent notice. Not gated: the failure notice is not a paid add-on
and checks no feature flag. The fail list ships as `dashboard.failList` — an
asset is listed once its failure has gone **30 days without a passing
re-test** (PRD § 6.8), computed from history on every read with **no stored
membership and no scheduled job**, and cleared by the next submitted pass —
and as `/wp/fail-list`, a drill-down behind the dashboard's Past due card,
oldest failure first, with two reachable age bands (30–60 days, over 60) as
row colouring driven by design tokens. An earlier cut listed assets the moment
the failure was submitted; that contradicted the PRD and was corrected. Copy is provisional pending client wording, like the four notice
defaults. Full writeups:
[Notice Workflow & Scheduler](/docs/notice-workflow#workflow-3--the-failure-notice)
and [WP Dashboard](/docs/wp-dashboard#the-fail-list).

**Workflow 2: AG Rate Renewal Notice (6.9)**: shipped. Creating an
agricultural customer queues one customer-scoped `ag_renewal` job (no asset)
for midnight Pacific/Honolulu on `ag_renewal_date`, in the same transaction as
the insert; a changed date reschedules it, leaving the agricultural rate
cancels it, and any other save leaves it alone. `0018` adds a partial unique
index allowing one live renewal job per customer. The handler is gated on
`ag_renewal_notice` at run time (missing or off cancels, unsent), sends to the
customer's **own** email through the shared frozen-payload delivery, and runs
as an **annual cycle** (team-lead decision, superseding the earlier "does not
auto-advance" answer): after a provider-confirmed delivery to an active
agricultural customer, the date becomes one calendar year after the Hawaii day
of that confirmation (29 February → 28 February in a non-leap year) and exactly
one next job is queued, atomically with completing this one. Counting from the
delivery, not from the notice's own date, is what gives a late notice a full
year to the next one. `0019` adds `scheduled_jobs.ag_renewal_date` — the date
each job is for — which is what stops a retry from adding a second year, and
`0020` adds `customers.revision`, the optimistic lock that stops a WP form
opened before the transition from putting the old date back. Copy in
`lib/ag-renewal-copy.ts` is provisional. Full writeup:
[Notice Workflow & Scheduler](/docs/notice-workflow#workflow-2--the-ag-rate-renewal-notice).

**Super-Admin (6.11)**: stays *in-progress*. The invite-new-WP action is wired and `/admin` is gated to `super_admin`. **WP impersonation has shipped.** `superAdmin.startImpersonation` and `endImpersonation` set and clear a separate `bfa_impersonation` cookie: `httpOnly`, HMAC-SHA-256-signed, one-hour lifetime. Its key is the new optional server variable `IMPERSONATION_COOKIE_SECRET`.

Every protected procedure and every route gate resolves the effective identity through one helper, `resolveEffectiveCaller`. It re-checks both accounts on every request, and no feature router carries impersonation code. The persistent banner and the WP list's Impersonate action now run through the server; the client-only demo store is gone. No migration ships with it.

Still open in this section: feature-flag toggles, and certifier impersonation (not in this pass). Full writeup: [Super-Admin Impersonation](/docs/super-admin-impersonation).

**Carries a new open question.** The WP list names purveyors, and the cookie has to name a profile. The shipped default targets the purveyor's **earliest-created active `wp_admin`**, the account the Contact column shows. It refuses purveyors with no active admin, and blocked purveyors. What should happen when a purveyor has several active admins is unconfirmed.

Every feature router's structured audit line keeps the real Super-Admin in `actor_id` and names the impersonated admin in `effective_profile_id`. The impersonation cookie is bound to the Supabase Auth `session_id` it was issued in, verified through the Auth server, so a new sign-in never resumes an old impersonation even if no client-side cleanup succeeds. Signing out and signing in still clear the cookie, best-effort. The certifier area is gated to the `certifier` role, so an impersonated WP admin is redirected to `/wp` and never reaches a shell without the impersonation banner.

**Transactional Email Integration (6.14)** stays *in-progress*, now only for its switch-on. The send helper and `consoleDriver` shipped with onboarding, and every mail path in the app runs through them. The Resend account exists, the sender domain `backflowreporter.io` is verified, and `providerDriver` is built and unit-tested, with `EMAIL_DRIVER`, `RESEND_API_KEY`, `RESEND_FROM_EMAIL` and `RESEND_REPLY_TO` in env validation; every Resend send sets `Reply-To` to `info@backflowreporter.io` so replies reach the existing mailbox. The email template design is also done: one shared, responsive layout in `packages/api/src/lib/email-layout.ts` wraps invitations (with a **Set up your account** button, fallback URL and expiry) and general-info broadcasts, and is the path automated notices will use; notice bodies stay escaped plain text, and branding is text-only until the client supplies a logo. What remains: set the variables in the deployment, enable `EMAIL_DRIVER=provider` after review, and confirm one live test send. Console stays the default until then. The automated notice copy is still awaiting client approval; that belongs to the workflows, not to 6.14. See [Invitations and Onboarding](/docs/invitations-onboarding#the-email-layer).

**Certifier Dashboard (6.3)**: shipped. The four leaf routes under the
certifier shell (`/certifier/drafts`, `/certifier/submitted`,
`/certifier/wizard`, `/certifier/profile` — the shell itself and its nav were
already built in 6.15) now have real screens: a `DraftsTable` (resume, delete),

gets a certifier's own read/write path for the first time —

policies with `certifier_id` in place of `water_purveyor_id`. A new
`certifierProcedure` (`packages/api/src/index.ts`) resolves and narrows
`ctx.caller.certifierId`, the same shape `wpProcedure` uses for
`waterPurveyorId`. Full writeup: [Certifier Dashboard](/docs/certifier-dashboard).

**Two deviations from the eight build-plan steps, both scope this task
absorbed rather than deferred.** First, the prototype's single "Dashboard"

Profile), not a fifth root route. A stat-card strip briefly sat atop
`/certifier/drafts` in its place; dropped on review as a redundant summary of

8) needed a write path `0006_certifier_policies` explicitly deferred as its

**Certifier WP Selector (6.4)**: shipped. The mock `use-active-wp.ts` store
6.3 flagged as a non-goal is now real: a new `certifier.listAuthorizedWps`
procedure returns the caller's own `active` authorizations, and `WpSwitcher`
in the certifier shell header switches between them, omitting whichever is
currently active. `0013_certifier_wp_authorization_policies` gives
`wp_certifier_authorizations` its first policy — a certifier reads their own
rows, any status, nothing else yet exists for it. The one change that reaches
back into 6.3's own procedures: `listDrafts`, `listSubmissions`, `getDraft`
and `deleteDraft` now take `waterPurveyorId` and scope by it alongside
`certifier_id`, so a certifier authorized for more than one purveyor sees only
the active one's rows — switching re-filters the whole dashboard, it does not
merge. Unlike `wpProcedure`, this id is a validated client input rather than
something resolved server-side, because a certifier's active WP has no single
source of truth on their profile; a new `assertAuthorizedWp` helper checks it
against the caller's own `active` rows before every use and is what a forged
id gets refused by. Selection itself lives in `sessionStorage`, per the
build-plan's own "client state for the session" wording — no cookie, no
server-side resolution. Left for the wizard (6.5): `assertAuthorizedWp` is
ready for the draft-creation procedure that doesn't exist yet.

**A Super-Admin DELETE gap 0012 finds and closes on the way in.** Granting
DELETE on `test_submissions` at all — needed for a certifier's own draft —
makes 0008's pre-existing `FOR ALL` Super-Admin policy newly cover DELETE too,
which would let a Super-Admin remove a submitted test that 0008 explicitly
said nothing removes. A RESTRICTIVE policy,
`test_submissions_delete_draft_only` (`status = 'draft'`), closes it by ANDing
against every permissive DELETE policy including that one, without touching
0008 itself.

## Known deviation from the kickoff runbook

Better-T-Stack actually scaffolded it as **`apps/fumadocs`** (package name `fumadocs`). ## Open questions blocking phase completion

Carried from [PRD § 10](/docs/prd#10-open-questions-for-the-client) — resolve before the owning phase is marked done:

- **Phase 2:** WPAdmin/WPsubAdmin/WPEmployee permission differences — all three currently share identical invitation policies; second-WP-invite notification behavior.
- **Phase 3:** signature vs. certify-checkbox; legacy PDF/results-document layout match (reference wizard: [bfr-temi-wiz-final.bubbleapps.io](https://bfr-temi-wiz-final.bubbleapps.io/version-test/wizard)).
- **Phase 6:** which account Super-Admin impersonation should use when a water purveyor has more than one active `wp_admin`. It currently uses the earliest-created one — see [Super-Admin Impersonation](/docs/super-admin-impersonation#which-account-a-purveyor-resolves-to).
- **Phase 5:** the full list of dynamic variables for notice text (six shipped, and the substitution layer takes a seventh as a list edit); **approved customer-facing copy for the four platform default notices**, which 6.6.7 ships as provisional placeholder text and Workflow 1 now actually sends; **where a held notice pipeline resumes**, shipped on the narrowest reading — see [the resume point](/docs/notice-workflow#the-resume-point-stated); **whether a terminally failed notice should stop the escalation**, shipped stopping it; monthly CSV export field list.

Resolved since the last pass (no longer blocking): mid-wizard pass/fail handling, scope of "edit submitted test data" for a WP, asset↔customer cardinality, email routing for suspended customers, and BIN reassignment on an existing asset — allowed, and logged with both values, which is what 6.6.2 shipped. See [PRD § 9](/docs/prd#9-confirmed-decisions-client-qa-log).
