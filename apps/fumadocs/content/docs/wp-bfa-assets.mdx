description: How a water purveyor registers and maintains the assemblies it is responsible for — the assets screen, its procedures, the customer-assignment transaction, and the row policies behind them
---

A BFA asset is the permanent record of one physical backflow assembly: its BIN,
what kind of valve it is, where it sits, and when it is next due to be tested.
It is the row every notice, every submission and every wizard prefill is keyed
on. Water purveyors create and maintain them from `/wp/assets`.

This page describes the screen as built. It covers *WP dashboard — BFA assets*
in the [build plan](/docs/build-plan) and PRD § 6.6.2.

## The customer joins are tenant-scoped

`listAssets` and `getAsset` both LEFT JOIN `customers` to put the current
occupant's name and status on the asset, and the detail view joins it again for
the occupancy history. All three match on the customer id **and** on the
caller's own purveyor.

The asset is scoped by `bfa_assets.water_purveyor_id`, but that does not scope
the customer: `current_customer_id` and `customer_assignments.customer_id` are
foreign keys to `customers`, and neither says the two share a tenant.
`assignCustomer` refuses to point one across — it validates the customer's
purveyor before writing — but a row written before that rule, a restore, or
corruption is not bound by it. Without the extra clause such a row would put
another purveyor's customer on an asset this caller is entitled to read.

The predicate is in the `ON` clause, so it fails safe. The asset comes back with
a null occupant, which is exactly how an unassigned asset already reads and a
state every screen already renders as "Unassigned"; in the `WHERE` the asset
itself would vanish from the list, hiding the row that needs repairing.

The history join changed from INNER to LEFT for the same reason. A
`customer_assignments` row is keyed by `bfa_asset_id` — the fact that an
occupancy existed is the purveyor's own record — so an INNER join carrying this
predicate would delete that fact whenever the customer it named turned out to be
foreign. The occupancy stays, the dates stay, and the name reads "Unknown
customer". On a correct database the two are identical; they differ only on the
mispointed row.

## What an asset record is

| Field | Required | Notes |
|---|---|---|
| `bin` | yes | Unique **per purveyor** — two WPs may number their valves the same way |
| `bfa_type` | yes | One of the eight types: RP, RPDA, RPDA-2, DC, DCDA, DCDA-2, PVB, SVB |
| `service_address` | yes | Searchable alongside the BIN |
| `assembly_location` | yes | Where on the property the assembly sits |
| `make`, `model`, `serial_number`, `size` | yes | Assembly details. Required on every WP save (WP/Admin feedback); the columns stay nullable, so a row saved before the rule — or built from a certifier submission — still reads, and editing it means filling them in |
| `annual_test_date` | yes on this screen | What the reminder workflow schedules against |
| `asset_status` | — | Computed by the scheduler; not editable by anyone |
| `current_customer_id` | no | Not on either form. Moves through the customer form's BIN or `assignCustomer` — see below |
| `water_purveyor_id` | — | Never sent by the client; derived from the caller |

Every text field has a maximum length, defined once in
`packages/api/src/lib/asset-field-limits.ts`. The Zod shapes are built from
those numbers and the form checks the same ones inline, so a value over the
limit is reported at its field (*Must be 100 characters or fewer.*) before it is
sent — rather than silently cut off, which a `maxLength` attribute does to a
pasted value. None of them
is a product rule — the columns are Postgres `text` and neither the PRD nor the
build plan puts a ceiling on a BIN or an address — they are input hygiene: wide
enough that no real value meets them, narrow enough that a pasted document does
not become a row.

### What the form checks, and what the server checks

The same required answers, in both places. **Add asset** opens with the
commonest answers already filled in (WP/Admin feedback): BFA type *RP* and
assembly location *After meter prior to any tees or branches*
(`newAssetValues` in `asset-form.tsx`). Both are ordinary editable values —
change them, or clear the location and the form asks for one like any other
required field. The edit form keeps whatever is stored, and `""` is never sent
to `createAssetInput`, whose enum check is unchanged. The form trims before it
judges, so a BIN of spaces reads as empty exactly as it does in
`createAssetInput`. The save button is never disabled for a missing answer:
pressing it reveals an inline message under each field that is still missing or
invalid and moves focus to the first one (the shared
[inline validation](/docs/design-system#form-validation) pattern). The annual
test date is typed as `MM/DD/YYYY` or chosen from the calendar picker and sent as the API's `YYYY-MM-DD`; it is
round-tripped through `Date` rather than pattern-matched, because `02/31/2027`
would otherwise parse to 3 March — the kind of wrong that surfaces months later
as a reminder that fired on a day nobody chose. The serial number stays free
text; only its length is checked.

A duplicate BIN is the one server refusal with a field of its own: `CONFLICT`
from `createAsset`/`updateAsset` is shown under the BIN input with the same
`aria-invalid`/`aria-describedby` wiring as a client-side error, and clears as
soon as the BIN is edited. Any other refusal is a form-level message above the
buttons — never a toast.

None of that is the boundary. Everything the form refuses, `createAssetInput` /
`updateAssetInput` refuse again, and the client half exists only so a request
that would be rejected is not sent.

One thing the form will not let happen at all, rather than validating: there is
no status control, because the scheduler owns it. The BFA type is a select over
exactly the eight enum values, so there is no free-text path into it. There is
no customer control — see below.

### Why the annual test date is required

The column is nullable, and the form still insists on a value. The client's
[confirmed answer](/docs/prd#9-confirmed-decisions-client-qa-log) is that the
annual test date is set by the WP *at the moment they assign the BIN* — it is
what [Workflow 1](/docs/notice-workflow) schedules the reminder and the three
late notices against, and the **sole** scheduling source: there is no second
due-date column anywhere. Every asset created from this screen is created with a BIN, so
an asset without a date would be one that can never be reminded about,
discovered months later by a notice that never fired. The column stays nullable
for rows that reach the table another way.

This is also the second half of the no-BIN submission flow (PRD § 7, flow 2): a
certifier may leave the BIN blank, and the WP later works out which assembly the
test belongs to, assigns the BIN here, and sets the date that puts it on the
schedule. And per flow 3, a WP can register an assembly directly with no
certifier submission behind it at all — that is what the **Add asset** button
does.

### Changing the date reschedules the chain

Correcting `annual_test_date` on an existing asset cancels **every** notice job
computed from the old one — including a reminder the scheduler is already
running — and inserts one fresh reminder for the new date, **in the same
transaction as the asset write**. Every stage hangs off that one field, so any
job left behind would be a notice about a deadline that no longer exists; a
running reminder that is cancelled cannot complete or schedule a late notice from
the old date.

Two guards keep this from being noisy. The reconciliation runs only when the date
actually moved — correcting a service address does not touch the schedule — and
it writes nothing when the chain is already one reminder at the right time, so a
redundant reconciliation writes nothing, moves no `updated_at` and emits no
scheduling line. Same rule as [a save that changes
nothing](#a-save-that-changes-nothing-writes-nothing).

A date already in the past still schedules a reminder, which is what lets a
long-overdue assembly catch up through the escalation rather than stay silent.

### Why the status is not on the form

`asset_status` is derived from `annual_test_date`: active, due soon, past due.
Letting somebody set it by hand would let the badge and the schedule disagree,
and the badge is the one people read. The form has no control for it, the two
mutations do not accept one, and — because a row policy cannot allow one column
and refuse another — `authenticated` was never granted the column at all. The
scheduler runs through the privileged connection and is unaffected.

It is now genuinely recomputed, on every scheduler tick, from the date on the
row: `past_due` once the due date has passed, `due_soon` from the reminder day up
to **and including** the due date, `active` otherwise — including an asset with
no date at all. The due date itself is not past due, because that is the last day
the test can still be done, which is why late notice 1 is due the day after. The
statement writes only the rows whose status is wrong, so an ordinary day changes
nothing. See [`asset_status` is
scheduler-owned](/docs/notice-workflow#asset_status-is-scheduler-owned).

### No customer control on either form

**Add asset** used to carry an optional customer dropdown. The WP/Admin feedback
removed it: a customer now reaches an asset from the [customer form's
BIN](/docs/wp-customers#the-bin), or from the asset's own page through
`assignCustomer`. Both close and open `customer_assignments` rows as they go.

`createAssetInput` still accepts an optional `currentCustomerId`, and
`createAsset` still opens the first assignment in the insert's transaction when
one is sent — a sound operation the notice-workflow suites build on — but no
screen sends it.

The **edit** form has no customer control either, and `updateAssetInput` does
not accept one. On an asset that already has an occupant, moving the pointer has
to close the outgoing occupancy row in the same transaction — a field there
would be the one way to change an occupant without recording it.

## Changing a BIN

Allowed, and never casual. Per the
[confirmed decision](/docs/prd#9-confirmed-decisions-client-qa-log), a WP may
correct any data it owns, the BIN included. What `updateAsset` adds is that the
correction is recorded: a change emits its own `bfa_asset_bin_changed` line
carrying the asset id, the old value, the new one and the acting profile —
separate from the generic `bfa_asset_updated` line, because the BIN is the most
protected value in the system and hiding its movement inside a general update
would be the same as not recording it.

A BIN that is already in use inside the same purveyor comes back as a
`CONFLICT` with the BIN in the message, from the unique constraint rather than
from a check-then-write — so there is no window between the check and the write
for a second clerk to take the same BIN. Uniqueness is checked on the server
only: a client-side pre-check would be a second answer that can disagree with
the constraint, and would still have to be re-checked at the write.

The screen carries that back to the field it is about. `CONFLICT` is raised for
exactly one reason, so the message goes under the BIN input with `aria-invalid`
and `aria-describedby` rather than into the form-wide banner, and it clears the
moment the BIN is edited — the refusal was about the value that was submitted,
and leaving it on screen would make a BIN the person has already fixed look
like it is still refused. Routing is by error code, not by matching the wording,
so the sentence can be rewritten without silently moving the message.

The edit form also warns *while* a BIN is being changed, not after saving: a
panel naming the value being left behind appears as soon as the field differs
from the record, and disappears if it is typed back. The warning is the point at
which the decision can still be taken back.

## The no-BIN asset

A certifier who has no BIN, or types one the register does not have, goes on
with no BIN (the wizard clears the field). At submit the test registers a fresh
asset from its own answers — type, service address, make, model, serial number,
size, location, and an annual test date one year after the test — **with
`bin` null** and **no customer**, and is linked to it (client, October 2026).
`0021` made the column nullable; a `CHECK` keeps a blank BIN `NULL`, never
`''`, and the existing per-purveyor unique constraint still applies to every
real BIN (Postgres treats NULLs as distinct).

Until it has a BIN the asset is **off the notice machinery**: no reminder chain
is scheduled for it, its tests' results are held — a fail queues no failure
notice and does not count toward the fail list — and the handlers cancel any
job that somehow reaches one. One rule enforces this in two places:
`applySubmittedTestResult` treats a test on a no-BIN asset as unlinked, and
`reconcileAssetNoticeChain` withdraws rather than schedules.

The asset page shows *No BIN*, a warning explaining the state, and **Assign
BIN** in place of *Edit asset*. Saving a BIN there — `updateAsset`, with the BIN
going from null to a value — **activates** the asset in the same transaction
(`activateAssetWithBin`): every submitted test on it has its result applied,
oldest first (a fail queues its notice now), and the reminder chain is
scheduled from the annual test date.

The customer is attached by hand (client: the WP *"manually link[s] the new
asset to a customer, keeping our master database clean"*), so the customer the
certifier typed is **never created or attached automatically**. It stays in the
test's answers, and while nobody is attached — before or after the BIN is
assigned — the page offers it as a suggestion (`getAsset` → `testCustomer`, from the latest
submitted test):

- **An existing customer has that email** — *Attach {name}* opens the usual
  attach dialog with them selected; the WP confirms, and a suspended customer
  still goes through its confirmation.
- **Nobody has it** — *Create customer from test* opens the customer form
  filled in from the test (standard rate, active, and this asset's BIN as the
  BIN to attach) for the WP to check and complete; saving creates the customer
  and `createCustomer` attaches them through that BIN. A new customer is always
  created through a BIN, so on an asset that has none yet the page says to
  assign the BIN first.

Ignoring the suggestion and attaching someone else works as for any asset. The [dashboard's No-BIN table](/docs/wp-dashboard#no-bin-reports)
lists every one still waiting.

If the assembly turns out to be registered already, the test is linked to that
asset from [Submitted Tests](/docs/wp-submitted-tests#from-a-no-bin-asset) and
the empty no-BIN asset is deleted.

## Assigning a customer

`assignCustomer` is three writes in one transaction:

1. close the open `customer_assignments` row by setting its `end_date`,
2. insert a new row with today's `start_date`,
3. move `bfa_assets.current_customer_id` to the new customer.

Both dates come from Postgres' `current_date` rather than from the Node process,
so the closing and the opening row cannot disagree about what day it is.

Doing only the third — the update a "current customer" field invites — would
answer *who gets the email* while quietly erasing *who had this valve last
year*, which is the question a disputed test needs. The
[confirmed cardinality](/docs/prd#9-confirmed-decisions-client-qa-log) is
many-changing-over-time in both directions, and this table is where that lives.

Three refusals worth naming:

- **A customer from another purveyor.** The customer is looked up inside the
  caller's own tenant, so a foreign id is never found rather than found and
  rejected, and the message says nothing about whether that uuid exists
  elsewhere. Nothing is written on the way out — no pointer moved, no half-open
  history. The screen cannot offer one either: the picker reads the same
  WP-scoped `listCustomers` the customers screen does.
- **The customer who is already attached.** Re-attaching them is not a
  reassignment. Writing anyway would close today's occupancy row and open an
  identical one beside it, turning one continuous tenancy into two — history
  recording a move nobody made. The procedure returns the asset unchanged and
  logs nothing; in the picker that customer is disabled and labelled *current*.
- **A suspended customer, unacknowledged.** See below.

### Suspended customers

Automated email goes to whichever customer is currently attached to the BIN. If
that customer is suspended, the asset's email pipeline stops entirely until a
different customer is attached — see [WP Customers](/docs/wp-customers). That
consequence belongs to the asset, so the asset shows it: *Suspended — email
paused* under the name in the table, and a warning panel on the detail view.

Because that consequence is large, attaching a suspended customer is not
something to reach by mis-clicking a list. `assignCustomerInput` carries an
`acknowledgeSuspendedCustomer` flag, defaulting to `false`, and the procedure
answers `PRECONDITION_FAILED` when the chosen customer is suspended and the flag
is absent. The default is the point: a client that has never heard of the flag
gets the refusal, not a silently muted asset.

The modal is how the flag gets set, not where the rule lives. Choosing a
suspended customer shows the warning beside the list; pressing **Attach
customer** then moves the dialog to a confirmation naming what stops, and only
that second press sends the acknowledgement. The order of the checks matters
too: the already-attached case is decided *before* the suspension gate, so a
customer suspended after they were attached does not turn a re-save into a
confirmation prompt for a change nobody is making.

**Attach customer** is not disabled while nothing is chosen: pressing it puts
*Choose a customer to attach.* under the picker and focuses it. A refusal from
`assignCustomer` is shown inside the dialog above its buttons, not as a toast,
and is cleared when the dialog closes.

An assignment made this way logs `to_customer_suspended: true` — the line that
explains why an asset's notices went quiet from that date.

Attaching an **active** customer is what ends the hold, and the same transaction
resumes the pipeline: the one stage that was waiting becomes due again, and
nothing already sent is replayed. A customer attached three months into an
escalation therefore receives the stage that was held, not the reminder and two
late notices the previous occupant's suspension swallowed. That resume point was
not specified by the plan and is a stated decision — see [the resume
point](/docs/notice-workflow#the-resume-point-stated).

The history table below the control is read-only. Nothing in the app edits a
`start_date` or an `end_date`: no procedure accepts one, and the row policies
grant `authenticated` only `end_date`, only on assignments whose asset the
caller can see, with no DELETE at all.

## Procedures

`assets.*` in `packages/api/src/routers/assets.ts`. All five sit behind
`wpProcedure`.

| Procedure | Does |
|---|---|
| `listAssets` | One page of the caller's own assets, ordered by BIN; filterable by status, searchable by BIN or service address |
| `getAsset` | One asset with its full occupancy history |
| `createAsset` | Registers one asset under the caller's purveyor, with its BIN, assembly details, initial annual test date and — optionally — its first customer |
| `updateAsset` | Rewrites one record — every field is sent, the BIN included |
| `assignCustomer` | The three-write transaction above |

`listAssets` is page-based rather than cursor-based: the screen shows a numbered
pager over a set measured in hundreds, and a page number is what the person
actually asks for. The count is over the whole filtered set, so *page 3 of 7*
stays true even when a page comes back empty. The search escapes `%` and `_`,
because somebody looking for `50%` means those three characters.

### A save that changes nothing writes nothing

Same rule as the customers screen. The whole record is sent on every save, so a
request that edits a field and one that opens the dialog and presses save look
identical on the wire. `updateAsset` compares the incoming values against the
row it already read and, when every writable column matches, returns that row
without touching the table — no `updated_at` bump, no `bfa_asset_updated` line,
and in particular no BIN-change line naming the same value twice.

### Where the tenant comes from

`ctx.caller`, and nowhere else. There is no `waterPurveyorId` on any input
shape, so a client cannot ask for another purveyor's tenant — there is no field
in which to ask. Every read and every write also carries the caller's purveyor
in its `where`, so a guessed uuid from another tenant matches no row and comes
back as a not-found rather than as a silent success.

All of these run through the privileged Drizzle connection, which bypasses RLS.
The procedure layer is the application's authorization boundary; the policies
below are a second, independent one.

## Row policies

`0004_bfa_asset_policies` adds the `bfa_assets` and `customer_assignments`
policies. RLS was enabled on both tables in the first migration; until now
neither had a policy, so nothing reaching them through PostgREST could see a
row.

| Policy | Who | What |
|---|---|---|
| `bfa_assets_all_super_admin` | `super_admin` | Read, insert and update, in every tenant |
| `bfa_assets_select_own_wp` | all three WP roles | Read rows where `water_purveyor_id` matches their own |
| `bfa_assets_insert_own_wp` | all three WP roles | Insert rows into their own purveyor |
| `bfa_assets_update_own_wp` | all three WP roles | Update rows in their own purveyor, and only into it |
| `customer_assignments_all_super_admin` | `super_admin` | Read, insert and update, in every tenant |
| `customer_assignments_select_own_wp` | all three WP roles | Read assignments whose asset they can see |
| `customer_assignments_insert_own_wp` | all three WP roles | Open an assignment when *both* the asset and the customer are theirs |
| `customer_assignments_update_own_wp` | all three WP roles | Close an assignment on an asset they can see |

Caller resolution goes through the `private.current_global_role()` and
`private.current_wp_id()` helpers from `0001`, so a blocked profile resolves to
NULL and keeps no access at all — same as everywhere else.

Four things worth stating outright:

- **`customer_assignments` has no tenant of its own.** Tenancy is read through
  the asset the row points at: you may see an assignment exactly when you may
  see its asset. That subquery is itself subject to `bfa_assets`' policies,
  which is what makes the coupling hold rather than merely look right.
- **The grants are column lists, not table grants.** `asset_status` is in
  neither the INSERT nor the UPDATE list, and `water_purveyor_id` is not in the
  UPDATE list, so the scheduler's column and the tenant cannot be written by
  `authenticated` at all. On `customer_assignments` only `end_date` is
  updatable — a past occupancy that can be edited into a different one is not
  history.
- **`WITH CHECK` as well as `USING` on both update policies.** They answer
  different questions — which rows can be reached, and what they may be turned
  into. The tenant column is already withheld by the grant; the policy says the
  same thing again for a future migration that widens it.
- **No DELETE for anybody, Super-Admin included.** An asset is referenced by
  occupancy history, by `test_submissions` and by `scheduled_jobs`; an
  assignment *is* the history. The `FOR ALL` Super-Admin policies still get
  nowhere, because the grants never handed DELETE over —
  `bfa-assets-rls.test.ts` asserts the refusal rather than trusting the reading.

There is no certifier read path yet. The wizard will need one — an asset
reachable through an active authorization, for BIN prefill — and it belongs with
the wizard; granting it now would open the tables to a role with no screen for
them.

## Audit logging

Every write emits one structured JSON line, the same shape as `customer_created`
and `caller_resolved`:

| Event | When |
|---|---|
| `bfa_asset_created` | An asset is registered, carrying its BIN, type and annual test date |
| `bfa_asset_updated` | A record actually changed — never for a save that changed nothing |
| `bfa_asset_bin_changed` | …and the BIN was part of what moved, carrying `from` and `to` |
| `bfa_asset_customer_assigned` | An occupancy changed, carrying `from` and `to` customer ids |

Each carries `actor_id`, `asset_id`, `wp_id` and `timestamp`.

## The screen

`/wp/assets`, in the standard WP shell. The table shows BIN, BFA type, service
address, current customer, annual test date and a status badge, with a search
box (BIN or service address, debounced), a status filter and a pager above and
below it. **Add asset** and per-row **Edit** open the same modal form —
`AddAssetForm` and `EditAssetForm` are that one field set with their starting
values and labels fixed, so the BIN and annual-test-date rules have one home.
The add variant additionally renders the optional customer dropdown; its list is
the WP-scoped `listCustomers`, fetched only once the dialog is open, because
most visits to this page never open it.

`/wp/assets?status=past_due` (or `due_soon`, `active`) opens the list with the
status filter already set — how the [dashboard's](/docs/wp-dashboard) Past Due
block links to the full list. The page reads the parameter on the server and
passes it to `AssetsTable` as `initialStatus`, a starting value only: the filter
stays changeable and is not written back to the URL. A repeated or unknown
`status` (checked by `isAssetStatus` in `asset-types.ts`, not the table: the page calls it on the server and the table is a client module) opens the unfiltered list.

A BIN links to `/wp/assets/[assetId]`: the assembly details, the current
customer with the control that changes them, and the full assignment history —
current occupancy at the top, every past one below it with its start and end
dates. Attaching a customer opens its own modal, so the choice, the suspended
warning and the confirmation are one focused decision rather than a control
sitting live on the page.

Design notes, from the [design system](/docs/design-system): the three statuses
use the success, warning and danger tint pairs (`active`, `due_soon`,
`past_due`), the page title is the only Sora on the screen, and colours come
from the tokens in `packages/ui/src/styles/globals.css` rather than hex values
in the components. The screen adds no new dependencies and no new `packages/ui`
primitives.

assets — same BIN, same service address — so a leak between them looks like a
leak rather than like a plausible row, and the shared BIN doubles as proof that
uniqueness is per purveyor.
